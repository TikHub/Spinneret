## 部署之前

### Spinneret 到底做什么？

它是一组爬虫节点或 API 节点的控制平面。它保存这些节点需要的身份（Cookie、设备参数、账号凭据）、代理、
配置和密钥；每个请求发给节点一个当下可用的身份加一个代理，并以租约的形式约束；再把节点上报回来的结果
变成冷却、封禁、健康分和熔断——全部在服务端完成，秒级生效，不需要重新部署节点。

节点只需要两样东西：服务端地址和一个 API 令牌。其余一切都在请求时下发。详见[核心概念](./04-concepts.md)。

### Spinneret **不**做什么？

它从不访问目标站点。它不含签名算法、不含登录流程、不做验证码识别、不做浏览器自动化、不解析 HTML。它不
替你发请求，不调度你的 URL，也不决定你的爬虫下一步做什么。请求始终由你的节点发出，Spinneret 管理的是
请求周围的那些状态。

v0.1 也不包含分布式全局限流、外部校验/刷新 Webhook、代理厂商适配器、OIDC、TOTP 和 mTLS。这些在
`CHANGELOG.md` 里被列为后续版本的候选项。

### 用它合法吗、合适吗？

Spinneret 是基础设施。它与站点无关：它不了解任何一个具体网站，不附带针对某个网站的集成，自己也发不出
任何请求。它持有的是你提供的凭据与调度状态，发出的是你的节点要它发的东西。

这意味着责任完全在你：节点访问哪些目标、这些请求受哪些服务条款和法律约束、往保管库里放了哪些凭据、你
是否有权使用它们，都由运营方负责。部署 Spinneret 不会让一次不合法的抓取变得合法，软件本身对你抓什么不
持立场。软件保护什么、哪些由你负责，见[安全](./19-security.md)。

### 必须要有 ClickHouse 吗？

不需要。ClickHouse 是可选的。它存放**请求明细**页背后的原始逐请求事件。把
`SPINNERET_CLICKHOUSE_URL` 留空，服务端启动时会打印 `clickhouse disabled: raw report events are not stored`
并正常运行——调度、上报、冷却、封禁、熔断、概览看板、冷却热力图和风险事件都读 PostgreSQL，全部照常工作。
只有请求明细页不可用。

不过随仓库发布的 Compose 栈里是带 ClickHouse 的，而且 `spinneret` 服务会等它健康之后才启动，所以要去掉
它得改 `deploy/compose/docker-compose.yml`。见[安装与部署](./02-installation.md)和
[配置参考](./03-configuration.md)。

### 那**必须**有什么？

PostgreSQL（事实来源）和 Redis 或 Valkey（热状态）。这两个是必需的。再加一个密钥加密密钥——
`SPINNERET_KEK_FILE` 或者直接内联的 `SPINNERET_KEKS`，两个都不给服务端就拒绝启动。见
[安装与部署](./02-installation.md)。

### 能不用 Docker 跑吗？

能。Spinneret 就是两个静态编译的 Go 二进制，其中一个内嵌了控制台：

```bash
make web          # 先把控制台构建到 web/dist
make build        # 产出 bin/spinneret-server 和 bin/spnr
```

单跑 `make build` **不会**构建控制台：没有先跑过 `make web` 时，二进制里只内嵌了一个占位文件，不提供任何
界面。

`bin/spinneret-server` 的全部配置来自 `SPINNERET_*` 环境变量，在同一个端口上
（`SPINNERET_HTTP_ADDR`，默认 `:8080`）提供内嵌的控制台和所有 API，不需要 CGO、不需要 sidecar、不需要额外的
Web 服务器。`bin/spnr` 负责跑迁移、创建第一个管理员、签发令牌，它是个纯命令行工具，不内嵌控制台。
PostgreSQL 和 Redis/Valkey 仍然要你自己准备。[安装与部署](./02-installation.md)里有 systemd 式的部署布局，
[命令行工具](./15-cli.md)里有两个二进制的全部参数，控制台构建的细节见[参与贡献](./20-contributing.md)。

### 我得重写爬虫吗？

不用。集成就是在你已有的那次请求前后各加一个调用：之前 `Acquire`，之后 `Report`。在 Python 和 Go SDK
里这是一个上下文管理器或者一个 `defer`，SDK 会把凭据和代理直接合并进你现有的 HTTP 客户端。见
[SDK 与示例](./14-sdks.md)。

### 怎么从自研调度器迁移过来？

按这个顺序来，任何一步之后停下都可以：

1. **先把已有的状态导进来。** `ImportIdentities` 批量接收你的 Cookie 和设备参数，`ImportProxies` 批量
   接收代理清单，控制台里也都有。见[身份与账号](./06-identities.md)和[代理池](./07-proxies.md)。
2. **先让一个节点走 Spinneret**，其余节点继续用老调度器。试运行期间身份不必被某一方独占；把
   `max_concurrent_leases` 调大一些，别让 Spinneret 和老代码抢同一个 Cookie。
3. **策略先开影子模式。** 动作策略写 `mode: shadow`，它会把每一个本该执行的动作记录下来但一个都不执行，
   于是你可以先观察一天，比对它的判断和你的判断，再让它有权封禁任何东西。见[策略](./08-policies.md)。
4. **把整个节点集群切过来**，然后把策略改成 `enforce`。
5. **配置最后迁。** 节点开始从配置中心读参数之后，改一个参数就不用再重新打镜像了。见
   [配置中心](./09-config-center.md)。

### 能不用真凭据先试试吗？

能。`./scripts/example-quickstart.sh` 会播下一个站点、20 个合成身份、两个模拟代理、已发布的策略和一个
节点令牌，然后跑一个完整的示例爬虫，去请求内置的、可以被你随时“弄坏”的模拟目标。全程不出本机。见
[快速开始](./01-quickstart.md)和[SDK 与示例](./14-sdks.md)。

## 关于模型

### 命名空间和租户有什么区别？我的“团队”是哪一个？

**租户**是硬隔离边界——一家公司、一个客户、一个组织，什么都不跨过去。**命名空间**是一个租户内部的分区：
一个环境（`prod`、`staging`）或者一条业务线。

你的团队几乎总是一个**命名空间**。只有当对方绝对不该看到你的任何东西时才用第二个租户——不同的客户、不同
的法律主体。站点、代理、策略、配置项、密钥和 API 令牌都属于某一个命名空间；令牌的命名空间在创建时就定死，
永远改不了。见[租户、用户与令牌](./11-access-control.md)。

### 站点、客户端、端点组分别是什么？

**站点**是一个目标系统。**客户端**是你对它使用的接入面（`web`、`mobile`、`partner`）——不同接入面通常需要
不同的 Cookie 和不同的请求头。**端点组**是站点加客户端之下的一类 URL，它们共享同一套限制和策略，比如
`search` 和 `detail`。节点把 URI 发过来，Spinneret 用站点的 URI 规则把它映射到某个端点组。见
[核心概念](./04-concepts.md)。

### 判断一个身份坏掉了的是我的节点还是服务端？

服务端。节点只上报**事实**：HTTP 状态码、可选的业务码、传输错误类型、耗时、响应大小，以及节点识别出来的
标记（`captcha_page`、`empty_list` 等）。信号策略把这些事实归类成 12 个判定结果之一并给出归因，动作策略
再把判定结果变成冷却、失效、隔离或封禁。要改变这套判断，改的是策略，不是节点。节点可以送一个
`outcome_hint`，但只有信号策略明确声明信任建议时才会被采用。见[策略](./08-policies.md)。

### Spinneret 会存我抓到的内容吗？

不会。一条上报携带的是 `report_id`、`lease_id`、`uri`、`method`、`http_status`、`business_code`、
`error_kind`、最多 32 个短 `markers`、可选的 `outcome_hint`、`latency_ms`、`response_bytes`、
`started_at`、`finished_at` 和一个 `release` 标志——完整的 wire 消息见[节点 API 参考](./13-node-api.md)。
没有任何字段用于响应体、请求体或响应头，服务端也没有地方放它们。请求明细页展示的就是这些元数据，仅此而已。

这里唯一需要你把关的是 `uri`：它按发来的原样存下来，包括查询串。如果你的查询串里带敏感信息，上报前先
把它剥掉。

### 身份和账号有什么区别？

**身份**是一套可以直接使用的凭据——一份 Cookie 加设备参数，或者一个 API Key。**账号**是若干身份共同归属的
那个登录主体。封禁一个账号会把它名下的所有身份一次性移出轮换，这正是 `account` 这个动作范围存在的理由。见
[身份与账号](./06-identities.md)。

### 必须用代理吗？

不必。轮换策略里 `proxy.mode: none` 是默认值，此时租约不带代理返回。代理池、健康检查和按站点的代理冷却，
只有在你设置了代理模式之后才参与进来。见[代理池](./07-proxies.md)。

### 两个节点会同时拿到同一个身份吗？

只有你允许时才会。`rotation.max_concurrent_leases` 默认是 `1`，即租约存续期间该身份在这个端点组内独占。
调大它可以允许并行使用，加 `reuse_interval` 可以强制两次使用之间的间隔，加 `quota` 窗口可以限制单个身份
每个周期的请求数。见[策略](./08-policies.md)。

### 节点持着租约挂掉了怎么办？

节点侧什么都不用做。每个实例每秒跑一次租约回收器，结束逾期租约、重新给身份打分，并把租约占住的可用性
还回去。节点上报过的租约结束为 `expired`；自始至终没有任何上报到达的租约结束为 **abandoned**（遗弃）。
被遗弃的租约不会出现在请求明细里——请求明细只存上报，而这里根本没有上报。它的计数在**概览**页的按节点
表格里，以及 `spinneret_lease_reaped_total{kind="abandoned"}` 上。你最多损失该身份一个租约有效期的产能。见
[核心概念](./04-concepts.md)和[可观测性与告警](./12-observability.md)。

### 身份明明是 `active`，为什么永远轮不到它？

因为生命周期状态和当下的可用条件是两回事。一个 `active` 身份此刻仍然可能不可用：端点组级或站点级的冷却、
已经达到 `max_concurrent_leases`、配额窗口用尽、复用间隔还没到、它的账号被冷却或封禁、绑定的代理不可用。
冷却热力图存在的意义就是把第二层可见化。见[故障排查](./18-troubleshooting.md)。

## 关于规模与成本

下面的数字是用 `test/load/` 里的压测工具、对着 Compose 栈测出来的，测试条件为单站点、
100,000 个身份、50 个端点组，全部跑在一台笔记本规格的 Docker 虚拟机里，压测生成器也在同一台机器上。把它们
当作曲线的形状来读，而不是对你自己硬件的承诺。方法、完整表格和全部注意事项见
[性能与调优](./17-performance.md)。

### 一套部署能扛多少 QPS？

单个服务实例、单个 Redis：

| 负载形态 | 稳定值 | 该速率下的延迟 |
| --- | ---: | --- |
| 完整 `Acquire` → `Report` 循环，独占租约（`max_concurrent_leases: 1`） | 4,500 次/秒 | acquire p99 1.86 ms，上报滞后 p99 9.3 ms |
| 完整循环，`max_concurrent_leases: 4` | 5,500 次/秒 | acquire p99 4.49 ms，上报滞后 p99 62 ms |
| 只算 `Acquire` | 4,993 次/秒 | p99 4.32 ms（不限延迟时峰值 7,792 次/秒） |
| `Report` 接收（accepted） | 44,437 条/秒 | 零拒绝 |
| `Report` 在 200 ms 目标内写入热状态 | 约 19,761 条/秒 | 滞后 p99 30.7 ms |

### 能撑多少身份和端点组？

一个站点 100,000 个身份、50 个端点组是实测数据集，而且离上限还远——单次 acquire 的热状态开销由
`rotation.candidate_sample`（默认 32）决定，和总共有多少身份无关。Redis 内存随**流量**增长，而不是随数据量
增长：上报去重标记和已结束的租约哈希会存活 `SPINNERET_REPORT_DEDUP_TTL`（默认 `1h`），上报流则保存尚未消费
的积压，上限为 `SPINNERET_STREAM_MAXLEN`（默认 1,000,000）。高上报速率上线前先把这两个值算好。

### 能接多少个节点？

真正的约束不是节点数，而是挂起的 `WatchConfig` 长轮询数量，因为每个订阅配置的节点都占着一个打开的请求。
单实例实测同时持有约 10,000 个订阅者，只花 0.05 个 CPU 核心，零失败；`SPINNERET_MAX_WATCHERS` 每实例默认
20,000，是硬上限。另一个约束是 acquire 流量，也就是上面那张表。

### 加一个副本能翻倍吗？

不能——这是性能那一页里最重要的一条运维事实。负载均衡后面两个副本合计只稳定在 **3,000 次循环/秒**，比单个
副本自己跑到的 4,500 次/秒还**少**。每个实例都用自己那份不设上限的并发去压同一个 Redis，一次失败的 acquire
大约要花成功 acquire 五倍的代价，越过拐点之后系统不是优雅降级而是拥塞崩溃。

实操建议：副本是为了**可用性**，不是为了吞吐；把实际负载压在实测拐点的 80% 以内；对
`spinneret_acquire_total{result="exhausted"}` 和 `spinneret_report_lag_seconds` 配告警。把
`SPINNERET_ROLE` 拆成 `api` 和 `worker` 实例，可以在不增加 acquire 并发的前提下扩上报处理能力。见
[性能与调优](./17-performance.md)和[运维手册](./16-operations.md)。

### 需要多少硬件？

v0.1 的容量假设——每个服务实例 4 vCPU / 8 GB，单个 Redis 实例——是成立的：在上述稳定速率下，一个服务实例用掉
1.4–1.6 个核，Valkey 用掉 1.6–1.9 个核（`io-threads 4`）。PostgreSQL 和 ClickHouse 的规格取决于你的保留期
设置，而不是请求速率。容量规划见[运维手册](./16-operations.md)。

### 运行成本是多少？

三个数据存储加一个无状态二进制。没有计量、没有回传、没有许可证服务器，软件也不调用任何外部服务。成本就是
PostgreSQL、Redis/Valkey 和（可选的）ClickHouse 的成本，加上实例本身。

## 关于安全

### 节点能读密钥吗？

只能读你允许的那些。节点令牌需要 `secret:read:<glob>` 权限范围，glob 参数是必填的，并且是拿
`<命名空间名>/<路径>` 去匹配的。命名空间 `prod` 下、带 `secret:read:prod/signing/*` 的令牌能读
`prod/signing/api_key`，别的都读不到。授权时给能用的最窄的那个 glob。见[密钥保管库](./10-secrets.md)，
以及[节点 API 参考](./13-node-api.md)里的 `GetSecret`。

### 节点能碰到别的租户的数据吗？

不能。令牌的租户和命名空间在创建时定死且不可更改，每个处理函数都会重新校验。要让一个节点访问两个命名空间，
就签发两个令牌。见[租户、用户与令牌](./11-access-control.md)。

### Cookie、密码和代理凭据存在哪？

存在 PostgreSQL 里，以 AES-256-GCM 密文形式、按信封加密组织：一个从不离开主机的密钥加密密钥（KEK）包裹
逐条记录的数据加密密钥（DEK），后者再加密身份载荷、代理 URL、密钥值、通知渠道配置，以及服务端自己的内部
密钥（`system_keys`）。拿到数据库转储但没有 KEK 的人，什么都还原不出来。见[密钥保管库](./10-secrets.md)；
加密列的完整清单见[安全](./19-security.md)。

### KEK 丢了会怎样？

所有加密值都不可恢复——身份载荷、代理凭据、密钥。没有托管、没有恢复密钥、没有救援通道。往系统里放任何真实
数据之前，先把 KEK 文件**和数据库备份分开**备好。见[密钥保管库](./10-secrets.md)和[安全](./19-security.md)。

### 控制台可以直接暴露到公网吗？

只有在 TLS 后面、并且读完加固清单之后才可以。除非你给它证书（`SPINNERET_TLS_CERT_FILE` /
`SPINNERET_TLS_KEY_FILE`）或者放在 TLS 终结器后面，否则 Spinneret 说的是明文 HTTP。`/metrics` 不需要认证
且暴露内部状态——用 `SPINNERET_METRICS_ADDR` 把它绑到单独地址上，别放在对外监听器上。pprof 监听
（`SPINNERET_PPROF_ADDR`）默认关闭，必须保证外部不可达。见[安全](./19-security.md)。

### 谁能看到明文凭据？

持有对应权限范围令牌的节点、持有 `identity:reveal` 或 `secret:reveal` 的控制台用户、任何能对着数据库运行
`spnr` 的人（这条路径完全绕过 API 和它的权限检查），以及任何在主机上有 root 的人。

每一次**明文查看**——`RevealSecret`、带 `reveal` 的 `GetIdentity`——以及每一次 `GetSecret` 都会写审计日志。
另外两条同样会交出真实凭据的路径**不**写审计：`Acquire`/`AcquireBatch` 是有意不写的，因为它在热路径上
（留下的记录是租约状态和请求明细），直连数据库的 `spnr` 也不写。见[安全](./19-security.md)。

### 发现漏洞怎么报？

不要发公开 issue。见[漏洞报告](./19-security.md#漏洞报告)。

## 关于运维

### Spinneret 挂了，我的节点会停吗？

部分会，取决于它当时在做什么：

| 节点动作 | 控制平面不可达期间 |
| --- | --- |
| 手上有有效租约 | 一直能干到租约有效期结束；请求本身根本不经过 Spinneret |
| `Acquire` | 失败。客户端没有兜底身份池——没有租约的节点发不出请求 |
| `Report` | 被缓冲。两个 SDK 都会把上报排队（默认 10,000 条，超出后丢最旧的）并按带抖动的指数退避重试 |
| `GetConfig` / `WatchConfig` | 两个 SDK 都可以回落到本地快照，带着最后一次取到的配置继续跑，并把 `from_snapshot` 置位。Python SDK 默认写快照，Go SDK 只在设置了 `SnapshotDir` 时写 |
| `GetSecret` | 失败；密钥没有快照 |

快照是磁盘上的普通 JSON 文件。引用了密钥的配置项根本不会被写入，除非 Python SDK 以 `cache_secrets=True`
启动——那样这些项会用 API 令牌派生出的密钥加密，而 Go SDK 会忽略它遇到的任何加密快照。见
[SDK 与示例](./14-sdks.md)。表里的每个 RPC 都在[节点 API 参考](./13-node-api.md)里有规范说明。

恢复之后有两件事要知道。上报按 `report_id` 在 `SPINNERET_REPORT_DEDUP_TTL`（默认 `1h`）内幂等，所以缓冲后
重发是安全的。但一条在租约结束 `SPINNERET_LATE_REPORT_WINDOW`（默认 `10m`）之后才到的上报属于**迟到上报**：
它仍然计入统计，但不再规划任何动作。也就是说，一次长时间中断损失的是风控信号，而不是正确性。见
[SDK 与示例](./14-sdks.md)。

### 有单点故障吗？

服务端是无状态的，副本想起多少起多少。单点在它下面那几层：

| 组件 | 丢了会怎样 |
| --- | --- |
| Redis / Valkey | Acquire 停摆。热状态是派生出来的，用 `spnr rebuild` 从 PostgreSQL 重建即可——没有永久性损失 |
| PostgreSQL | 全停。这是事实来源，务必备份并演练恢复 |
| KEK 文件 | 所有加密值不可恢复。必须和数据库分开备份 |
| ClickHouse | 只有请求明细页停摆，其余照常 |

Redis Cluster 是支持的——把 `SPINNERET_REDIS_ADDRS` 设为种子节点，客户端就以集群模式连接——但本套文档里的
每一个压测数字都是在单实例上测的，而且当前的吞吐上限来自争用，不是 Redis CPU。见
[运维手册](./16-operations.md)。

### 怎么做多地域部署？

Spinneret 自身不做跨地域复制。两种可行形态：

- **一套控制平面，节点分布在多个地域。** 最简单。节点为每次 `Acquire` 付一个跨地域往返，为每批上报再付一个；
  上报是批量且异步的，所以真正要在意的是 acquire 的延迟。按地域选代理是策略层面的事
  （`proxy.mode: region_match`），不是部署层面的事。
- **每个地域一套部署**，各自带自己的 PostgreSQL、Redis 和命名空间。身份不共享——当身份本身就绑定地域时，
  这通常正是你想要的。

如果 acquire 路径上的跨地域往返无法接受，或者某个地域必须能在另一个地域整体失效时独活，就选第二种。见
[运维手册](./16-operations.md)。

### 怎么安全升级？

1. 备份 PostgreSQL，确认 KEK 备份还在。
2. 读这个版本的 `CHANGELOG.md`——迁移项和「上线后不可更改」的东西都会在那里点名。
3. 跑迁移：`spnr migrate up`（Compose 栈会在服务端启动前，以 `migrate` 服务的形式跑它）。
4. 副本逐个滚动。数据库版本**领先于**二进制的服务端——滚动过程中的常态——会带警告启动而不是拒绝启动，所以
   滚动升级是可行的；数据库**落后于**二进制时，是自动迁移还是直接拒绝，取决于你的启动方式。
5. 滚动收尾期间盯住 `spinneret_report_lag_seconds` 和 acquire 的错误计数。

**警告。** `SPINNERET_REPORT_SHARDS`（默认 `16`）一旦更改就会让在途租约变成孤儿。上线前就把它定下来。见
[运维手册](./16-operations.md)和[命令行工具](./15-cli.md)。

### 怎么备份？

PostgreSQL 用你惯用的转储或快照机制，KEK 文件单独备——没有 KEK 的转储读不出来，没有转储的 KEK 也没用。
Redis 不需要备份：`spnr rebuild` 会从 PostgreSQL 把热状态重建出来。ClickHouse 存的是原始请求事件，保留期由
`SPINNERET_CLICKHOUSE_TTL_DAYS`（默认 `90`）控制，一般不值得备份。恢复演练见[运维手册](./16-operations.md)。

### 怎么在不搞坏生产的前提下验证策略改动？

三个工具，按投入程度递增：**规则调试器**拿一条构造出来的上报去回放当前生效的策略，告诉你命中了哪条规则；
**影子模式**（`mode: shadow`）记录策略本该执行的每一个动作但一个都不执行；**版本回滚**一步把上一个已发布
版本换回来。见[策略](./08-policies.md)。

### 应该监控什么？

至少这些：`spinneret_acquire_total{result="exhausted"}`（池空了）、`spinneret_report_lag_seconds`（Worker
跟不上了）、`spinneret_acquire_duration_seconds`（拐点），以及把 `identity_low_watermark`、
`proxy_low_watermark`、`report_backlog`、`breaker_opened` 这几类告警接到通知渠道上。见
[可观测性与告警](./12-observability.md)。

### 能直接清空 Redis 吗？

能，只要是有意为之。热状态是从 PostgreSQL 派生的，`spnr rebuild` 会把它重建出来。三点提醒：在途租约会丢失
（对应请求失败后重试）；**全量**重建——不带 `--site` 的 `spnr rebuild`——会让所有 API 实例在重建完成前上报
not-ready，负载均衡会把它们摘下去，而 `spnr rebuild --site <name>` 只重新物化一个站点，其余部分照常服务；
另外刚重建完的站点在一段时间内比预热过的站点更贵——所有端点组都从同一份就绪队列排序开始，会在同一批候选上
撞车，直到流量把它们错开。能挑低峰期就挑低峰期。见[运维手册](./16-operations.md)和
[命令行工具](./15-cli.md)。

## 术语表

按中文术语的拼音排序，以拉丁字母开头的术语排在最前面。代码里的标识符保持原样。

| 中文 | English | 释义 |
| --- | --- | --- |
| API 令牌 | API token | 节点用来认证的 `spn_…` Bearer 凭据。它终生绑定一个租户和一个命名空间，并携带一份固定的权限范围清单。 |
| ClickHouse | ClickHouse | 可选的分析型数据库，存放原始的逐请求事件。没有它，系统其余部分照常工作，只有请求明细页不可用。 |
| CSRF 请求头 | CSRF header | 控制台在非安全方法上必须带的 `X-Spinneret-CSRF: 1` 请求头。正是它的缺失，挡住了别的网站冒充已登录操作者。 |
| DEK（数据加密密钥） | DEK (data-encryption key) | 加密某一条存储值的逐条记录密钥。它自己也是加密存放的，由密钥加密密钥包裹。 |
| KEK（密钥加密密钥） | KEK (key-encryption key) | 主密钥，以文件形式放在主机上，用来加密每一个数据加密密钥。它从不进入数据库。丢失它意味着所有加密值不可恢复。 |
| Valkey | Valkey | Compose 栈用来承载热状态的 Redis 兼容服务端。任何说 Redis 协议的实现都可以用；压测数字和调优结论是在 Valkey 上得到的。 |
| `_runtime` 分组 | `_runtime` group | 一个保留的只读配置分组，把实时运行状态——熔断器状态和站点开关——通过和普通配置相同的订阅协议暴露给节点。 |
| 版本令牌 | version token | 节点在订阅配置时带上的那个普通 `int32`，用来声明自己已经持有某个配置项的哪个版本（`0` 表示没有）。已发布版本与它**不同**时服务端立即应答——回滚正是靠这一点送达节点——两者相等时请求被挂起。 |
| 半开 | half-open | 失败探测器的试探状态：它曾被触发，等待期已过，现在放行少量试探请求，看端点是否恢复。 |
| 背压 | backpressure | 从饱和的环节往回传给上游的“慢一点”信号。在这里它表现为上报滞后增长，以及 acquire 被拒。 |
| 标记 | marker | 节点针对识别出的响应特征附在上报上的短标签——`captcha_page`、`login_redirect`、`empty_list`。每条上报最多 32 个，是状态码之外最主要的归类输入。 |
| 草稿 | draft | 已编辑但未发布的策略或配置项版本。节点永远看不到草稿；发布是一个单独的、单独授权的动作。 |
| 策略 | policy | 一份有名字、有版本的 YAML 文档，用来约束行为。共四类：轮换、信号、动作、熔断。 |
| 策略绑定 | policy binding | 把一份策略挂到某个范围上——命名空间、站点、客户端或端点组。最具体的绑定生效，因此可以用一份基础策略覆盖整个集群，再叠加少数窄例外。 |
| 长轮询 | long poll | 服务端一直挂着、直到有变更或超时才返回的请求。它让节点在毫秒级知道配置变了，而不必循环轮询。 |
| 迟到上报 | late report | 在租约结束 `SPINNERET_LATE_REPORT_WINDOW`（默认 `10m`）之后才到达的上报。它仍计入统计，但不再规划任何处置。 |
| 重建 | rebuild | 用 `spnr rebuild` 从 PostgreSQL 重新生成 Redis 工作集。任何时候都可以跑，而且不会丢掉在途租约；刚重建的站点在短时间内更贵。只有在重建之前真的清空了 Redis，租约才会丢。 |
| 代理 | proxy | 存在池子里的一条出口线路，带 URL、类型、地域、供应商和标签。它的凭据和其他密钥一样加密落盘。 |
| 代理池 | proxy pool | 一个命名空间可用的全部代理，连同它们的健康检查结果、按站点的冷却和身份绑定关系。 |
| 代理分配模式 | proxy assignment mode | 租约怎么拿到代理：`none`（不带代理）、`pool`（任意匹配的一个）、`bind_identity`（该身份绑定的那一个）或 `region_match`（地域与身份一致的那一个）。 |
| 订阅者 | watcher | 一次被挂起的 `WatchConfig` 调用。不论这一次调用订阅了多少个配置项（最多 200 个），一个节点都只占一个，因此 `SPINNERET_MAX_WATCHERS`（每实例默认 `20000`）界定了集群规模上限。 |
| 低水位 | low watermark | 可用身份或可用代理数量低于该阈值即视为危险。跨过它会触发告警。 |
| 动作 | action | 服务端归类完一条上报之后，对身份、账号或代理施加的处置：`cooldown`、`expire`、`quarantine`、`ban` 或 `activate`。 |
| 动作策略 | action policy | 决定哪个判定结果引出哪个动作、作用在哪个范围、退避和升级怎么走、健康分驱动什么行为的那份策略。 |
| 端点组 | endpoint group | 同一站点、同一客户端之下共享限制和策略的一类 URL，例如 `search` 或 `detail`。节点发来的 URI 由站点规则映射到其中之一。 |
| 封禁 | ban | 把一个身份、账号或代理按指定时长或永久移出轮换。自动处置里最重的一档。 |
| 风险事件 | risk event | 一次被记录下来的高危时刻：封禁激增、失败探测器触发、身份池抽干。它有独立的控制台页面，也可以路由成告警。 |
| 副本 | replica | 负载均衡后面若干可互换的服务实例之一。副本带来可用性，但不会让吞吐翻倍，因为它们争抢同一个 Redis。 |
| 复用间隔 | reuse interval | 同一个身份两次使用之间的最小间隔，起算点可以是上一个租约的租借时刻，也可以是归还时刻。 |
| 告警规则 | alert rule | 判断何时触发通知渠道的那个条件，写在某个指标或者某类告警上。起步模板在可观测性那一页。 |
| 隔离 | quarantine | 把一个身份——或者一个代理——按固定时长移出轮换，期满之后它必须重新证明自己，而不是直接恢复完全信任。通常由健康分崩塌触发。 |
| 关闭 | closed | 熔断器的正常状态：acquire 照常通过。半开状态下放行的试探请求足够成功之后，熔断器回到这个状态。 |
| 归还 | release | 结束一个租约，让身份重新可用。节点通常不是单独发一次调用，而是在最后一条上报上带 `release: true`。 |
| 归因 | blame | 一次判定结果该算在身份头上、代理头上、两者都算还是都不算。惩罚身份的规则只在身份被归因时才触发。 |
| 规则调试器 | rule debugger | 控制台里的工具，拿一条构造出来的上报去回放当前生效的策略，展示命中了哪条规则、会发生什么。 |
| 候选采样数 | candidate sample | 一次 `Acquire` 中调度器从就绪集合里取出多少个身份，再交给轮换策略挑选。`rotation.candidate_sample`，默认 `32`。 |
| 会话 | session | 已登录的控制台会话，由一个 `HttpOnly`、`SameSite=Strict` 的 Cookie 承载，寿命为 `SPINNERET_SESSION_TTL`（默认 `12h`）。与节点的无状态令牌认证无关。 |
| 会话粘性 | sticky session | 把一个身份在一段时间内固定到某个会话键上，使多步流程始终使用同一套凭据。按轮换策略开启，会话键随 `Acquire` 送上来。 |
| 健康分 | health score | 每个身份 0–100 的滚动分数，按指数加权从每次结果更新，并随时间衰减。低分会导致冷却、移出轮换或降低被选中的权重。 |
| 交叉归因 | cross attribution | 当证据指向其中一方时，把风险在身份和它所经过的代理之间重新分配。在动作策略里配置。 |
| 节点 | node | 你自己那台真正发请求的机器：爬虫、Worker、API 客户端。Spinneret 自己从不发请求。 |
| 角色 | role | 一组有名字的权限集合。共四个：`viewer`、`operator`、`admin`、`owner`，权力依次增大。 |
| 角色绑定 | role binding | 把某个角色授予某个用户的那条授权，作用在一个租户上，并可收窄到某个命名空间及其部分站点。光有用户账号本身不授予任何权限。 |
| 客户端 | client | 对目标使用的接入面，例如 `web`、`mobile`、`partner`。不同接入面通常需要不同的凭据和请求头。 |
| 控制平面 | control plane | 掌管请求周围状态的那套系统——用哪份凭据、走哪个代理、端点当下能不能用——与真正发请求的那些机器相对。 |
| 冷却 | cooldown | 一个时间戳，在它之前某个对象不可用。可作用在端点组、站点、身份、账号或代理范围上，并随失败重复而指数变长。 |
| 冷却热力图 | cooldown heatmap | 控制台页面，纵横两轴是身份与端点组，每个格子按“此身份此刻能否服务该组”着色。 |
| 轮换策略 | rotation policy | 决定一次 `Acquire` 拿到哪个身份的策略：哪些身份类型可用、选择算法、租约时长、并发度、复用间隔、配额、粘性和代理模式。 |
| 幂等键 | idempotency key | 每条上报上由客户端生成的 `report_id`。去重窗口内用同一个值重试会被计为重复，不产生任何额外效果。 |
| 密钥 | secret | 位于某个路径（例如 `signing/api_key`）下、有名字、有版本的加密值。可以被带匹配权限范围的节点读取，也可以被配置项引用。 |
| 密钥保管库 | secret vault | Spinneret 中负责以信封加密存放密钥、为其做版本管理、审计每一次读取并支持在线密钥轮换的那部分。 |
| 密钥引用 | secret reference | 配置项里的 `${secret:<path>}` 占位符。节点读取该项时由服务端解析——前提是这个节点的令牌同样有权读取被引用的路径。 |
| 命名空间 | namespace | 一个租户内部的分区——一个环境或一条业务线。站点、代理、策略、配置项、密钥和令牌都只属于其中一个。它通常就是团队这一层。 |
| 明文查看 | reveal | 在控制台里显示一份存储的明文——身份载荷或密钥值。它需要专门的权限，且每一次查看都会被审计。 |
| 排空 | drain | 优雅地把一个服务实例摘出去：停止接新活，做完在途的，然后退出。 |
| 判定建议 | outcome hint | 节点在自己的上报里提出的归类建议。除非信号策略被明确配置为信任建议，否则它被忽略。 |
| 判定结果 | outcome | 服务端对一条上报的归类，恰好 12 种：`success`、`empty`、`rate_limited`、`captcha`、`auth_invalid`、`forbidden`、`banned`、`proxy_error`、`network_error`、`target_error`、`client_error`、`unknown`。 |
| 配额 | quota | 单个身份在某个端点组内每个时间窗口的请求数上限，按滑动窗口估算。可以同时生效多个窗口。 |
| 配置分组 | config group | 命名空间内一组配置键的命名文件夹，例如 `crawler`。令牌的权限范围是按分组授予的。 |
| 配置项 | config item | 配置分组里的一个键，内容是 JSON、YAML 或纯文本，并带草稿、发布和回滚的版本管理。 |
| 配置中心 | configuration center | Spinneret 中为节点保存带版本的配置、并把变更推给它们的那部分，使得改一个参数不必重新打镜像。 |
| 凭据 | credential | 节点随租约收到的那份具体的 Cookie、请求头、查询参数和请求体字段，由身份类型的投递模板从存储字段渲染而来。 |
| 平台管理员 | platform administrator | 被标记为 `is_platform_admin` 的用户。他们在每个租户里通过每一项权限检查，包括密钥管理。没有任何配置能限制他们。 |
| 请求明细 | request explorer | 控制台页面，逐条列出被上报的请求及其判定结果和归因。它是唯一需要 ClickHouse 的页面。 |
| 权限 | permission | 控制台授权模型里的单个权利，写作 `resource:verb`，例如 `identity:reveal` 或 `policy:publish`。角色就是它们的集合。 |
| 权限范围 | scope (token) | API 令牌权限清单里的一条，例如 `lease:acquire:example-site` 或 `secret:read:prod/signing/*`。令牌只能做它的权限范围允许的事。 |
| 热状态 | hot state | Redis/Valkey 里的工作集：就绪队列、租约、冷却、计数器和上报流。完全由 PostgreSQL 派生，也可以从它重建。 |
| 熔断 | open | 熔断器被触发之后的状态：该端点组的 acquire 直接被拒，直到等待期结束、转入半开。 |
| 熔断策略 | breaker policy | 配置端点组级失败探测器的那份策略：窗口大小、阈值、触发后保持多久、恢复期放行多少试探请求。 |
| 熔断器 | circuit breaker | 端点组级的开关，当近期失败率或风险率越过阈值时拒绝 acquire，以免持续冲击一个正在出问题的端点。 |
| 上报 | report | 节点在一次请求之后送来的记录，只带事实：状态码、业务码、传输错误类型、耗时、大小、标记和时间戳。绝不包含响应内容。 |
| 上报分片 | report shard | 上报被分布到的 `SPINNERET_REPORT_SHARDS`（默认 `16`）个 Redis 流之一，每个由一个 Worker 独占。上线后更改数量会让在途租约变成孤儿。 |
| 身份 | identity | 一套面向目标可直接使用的凭据——一份带设备参数的 Cookie，或者一个 API Key。它是被租借、冷却、打分和封禁的那个单位。 |
| 身份类型 | identity type | 站点之下身份的结构定义：存哪些字段、哪些必填、以及怎样投递给节点。 |
| 身份生命周期状态 | identity lifecycle state | 一个身份处在生命周期的哪一段，与它此刻是否可用是两回事：`pending`、`active`、`expired`、`banned`、`quarantined`、`disabled` 或 `retired`。 |
| 审计日志 | audit log | 记录谁通过 API 做了什么：操作者、动作、目标、时间和来源地址。管理类操作和每一次明文查看都会写入。 |
| 升级阶梯 | escalation ladder | 一个有序列表，使同一对象重复被临时封禁时，每一次都比上一次更长。 |
| 失败连击 | failure streak | 某个对象连续失败的次数。它是指数冷却退避的指数，并在可配置的一段平静期后清零。 |
| 实例 | instance | 一个正在运行的 `spinneret-server` 进程。实例无状态、可互换，状态在 PostgreSQL 和 Redis 里。 |
| 失效 | expire | 把身份标记为在存储字段被刷新之前不可用。通常是对目标判定凭据无效的响应。 |
| 探针租约 | probe lease | 用来试水的租约：要么发给失败探测器处于半开状态的恢复中端点，要么发给刚导入、尚未证明自己的身份。 |
| 通知渠道 | notification channel | 配置好的告警去向。共支持五种类型，每种的配置字段见[可观测性与告警](./12-observability.md)；其中 `webhook` 是通用的那一种，带 HMAC 签名。 |
| 投递模板 | delivery template | 身份类型中规定存储字段如何变成一个请求的那部分——哪个字段变成 Cookie、哪个变成请求头、哪个变成查询参数。 |
| 吞吐 | throughput | 每秒完成的有效工作量。这里按每秒完成的 `Acquire`→`Report` 循环数计，而不是按原始请求数计。 |
| 尾延迟 | tail latency | 延迟分布的慢端——p99 及以上。过载总是先在这里显形，远早于均值发生变化。 |
| 信号策略 | signal policy | 把原始上报归类成判定结果并给出归因的那份策略，条件可以写在状态码、业务码、错误类型、标记、URI、方法、耗时和大小上。 |
| 信号规则 | signal rule | 信号策略里的一条「条件—结果」条目。第一条命中的规则决定归类。 |
| 续约 | renew | 在租约即将到期时延长它，上限是租约最长存续。用于耗时超过初始租期的请求。 |
| 影子模式 | shadow mode | 让动作策略以 `mode: shadow` 运行，它会记录本该施加的每一个处置但一个都不施加。这是拿线上流量零风险评估策略改动的办法。 |
| 拥塞崩溃 | congestion collapse | 一种故障形态：负载增加反而让总有效工作量**下降**，因为争用让每次操作更贵，而更贵又进一步加剧争用。 |
| 预热 | warm-up | 身份被激活之后的一段时间，其配额被按比例缩小，使新凭据被缓慢带入流量，而不是一上来就满速使用。 |
| 载荷 | payload | 身份被加密存储的那些字段——Cookie、令牌、设备参数本身，与节点收到的那份渲染结果相对。 |
| 载荷版本 | payload version | 身份存储字段的修订计数。刷新字段会让它加一，节点据此可以判断自己手上的凭据已经过期。 |
| 站点 | site | Spinneret 所建模的一个目标系统，其下挂着端点组、URI 规则、身份类型和身份。除了这条记录，Spinneret 对真实系统一无所知。 |
| 站点开关 | site switch | 操作者控制的整站暂停。开着的时候，该站点的 acquire 会以一个专门的原因被拒绝，而不是逐个失败。 |
| 账号 | account | 若干身份可以共同归属的一个登录主体。封禁或冷却一个账号，会把它名下所有身份一次性移出轮换。 |
| 指数加权移动平均 | EWMA | 一种把近期样本权重放大的滑动平均。健康分靠它既能跟上变化，又不会因为一次失败就过度反应。 |
| 种子数据 | seed | `spnr seed` 创建的合成演示或压测数据：一个站点、若干端点组、身份、已发布的策略、一个配置项和一个节点令牌。可重复执行：已存在的对象保留，但节点令牌会被重新创建，旧的那个被吊销。 |
| 准入控制 | admission control | 限制一个服务实例同时处理多少请求，使过载被廉价地拒绝，而不是把吞吐拖垮。v0.1 未实现；它本该解决的过载行为在性能页里有描述。 |
| 租户 | tenant | 硬隔离边界：一家公司、一个客户、一个组织。除了服务进程、数据库和运营方管理的密钥之外，租户之间什么都不共享。 |
| 租借 | acquire | 在某一个端点组上取得某一个身份的租约。节点在每次请求之前做的就是这件事；对应的 RPC 叫 `Acquire`。 |
| 租约 | lease | 对某一个身份、在某一个端点组上的限时占用。正是它让服务端知道此刻有多少节点持有该身份，并能对其设限。 |
| 租约回收器 | lease reaper | 每个实例每秒跑一次的循环，结束过期租约、重新给身份打分、把租约占住的可用性还回去。这就是为什么一个崩掉的节点最多只损失一个租约有效期。 |
| 租约有效期 | lease TTL | 一次 `Acquire` 或 `Renew` 授予的租约时长。`rotation.lease_ttl`，默认 `2m`。 |
| 租约最长存续 | lease lifetime | 无论续约多少次都无法越过的租约上限。`rotation.max_lease_lifetime`，默认 `30m`。 |
