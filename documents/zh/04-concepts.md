## 控制平面与节点

控制平面掌管请求周边的**状态**，并按请求逐次发放：此刻哪个身份可用、走哪个代理、这个端点是否正在熔断、
节点的配置和密钥是什么。节点掌管**请求本身**：构造、签名（如果目标站需要）、发送、解析响应，然后把结果上报回来。

Spinneret 永远不会访问目标站点。它不含签名算法、不含登录流程、不含验证码破解。它对目标站的全部认知，
都来自节点上报的内容。

```text
节点                                     Spinneret
 |  Acquire(site, client, uri)  ----->  选择身份 + 代理，开出租约
 |  <----- 身份 + 凭据 + 代理 + lease_id
 |
 |  ... 节点向目标站发出请求，读取响应 ...
 |
 |  Report(lease_id, status, markers, latency)  ----->  分类、冷却、
 |                                                      封禁、评分、熔断
```

节点自身只需要两个配置值：服务端地址和一个 API 令牌。其余一切都在请求时获取，所以修改冷却规则、
新增身份或暂停站点都能在数秒内生效，无需重新部署任何节点。

## 隔离模型：平台、租户、命名空间

三层。**租户**是硬隔离边界；**命名空间**是租户内部的分区，也是实际意义上的"团队"单位。
每一份业务数据都恰好属于一个命名空间。

```text
平台
└── 租户  "acme"                        硬隔离边界
    ├── 命名空间  "prod"                 团队 / 环境单位
    │   ├── 站点
    │   │   └── 站点  "example-site"
    │   │       ├── 客户端        web、mobile、partner
    │   │       ├── 端点组（按客户端）    search、detail、_default
    │   │       │   └── URI 规则
    │   │       ├── 身份类型（按客户端）  web_cookie、app_device
    │   │       ├── 账号
    │   │       └── 身份
    │   ├── 代理池                        命名空间内所有站点共用
    │   ├── 策略 + 策略绑定
    │   ├── 配置分组 → 配置项
    │   └── 密钥（保管库路径）
    └── 命名空间  "staging"
        └── …… 完全独立的数据
```

这带来的直接结果：

| 问题 | 答案 |
| --- | --- |
| `prod` 命名空间的用户能看到 `staging` 的身份吗？ | 不能。身份、凭据、代理、账号、策略、配置项、密钥和审计记录全部按命名空间隔离。 |
| 租户 A 的用户能看到租户 B 的任何东西吗？ | 不能。用户的角色绑定按租户授予；在某租户没有绑定的用户根本看不到这个租户。 |
| 谁能看到全部？ | 平台管理员（`users.is_platform_admin`）。`tenant:manage` 与 `kek:manage` 两个权限也只有平台管理员能持有。 |
| API 令牌的作用范围是什么？ | 恰好一个命名空间，创建令牌时确定。节点无论请求什么，都无法触达其他命名空间。 |

用户通过**角色绑定**获得访问权。一条绑定包含租户、角色（`viewer`、`operator`、`admin`、`owner`）、
可选的一个命名空间、可选的站点 ID 列表，以及可选的少量额外权限。不指定命名空间的绑定作用于该租户的
所有命名空间；带 `site_ids` 的绑定把站点级权限限制在这些站点内。

节点流量完全不使用角色。`lease:acquire`、`report:write` 和 `secret:read` 是节点专属权限，
只能通过 API 令牌的权限范围授予。

完整权限清单见[租户、用户与令牌](./11-access-control.md)。

## 寻址模型：站点、客户端、端点组

节点从不说"把身份 X 给我"，它只描述**自己将要做什么**，由 Spinneret 把这个描述解析成一套配置。

```text
站点            example-site        一个目标，一个命名空间
 └── 客户端     web | mobile | partner
      └── 端点组         search | detail | _default
           └── URI 规则   /api/search*  →  search
```

- **站点**是命名空间内的一个目标系统，名称在命名空间内唯一。
- **客户端**是访问该站点的一种形态：`web`、`mobile`、`partner`。站点声明自己拥有哪些客户端（默认只有 `web`）。
  身份类型、端点组和身份都归属于具体的站点**加**客户端——移动端的身份不能当作 web 身份使用。
- **端点组**是同一站点、同一客户端下行为相近的一组端点。每个站点 + 客户端都必然有一个名为 `_default` 的端点组。

### 为什么需要端点组

从风控角度看，同一站点的两个端点通常**并不等价**。列表端点可能每个身份每小时只能发 60 次请求就开始返回验证码，
而详情端点可以发几千次；其中一个可能在 09:00 开始失败，另一个完全正常。如果冷却、配额、健康分和熔断器都按站点记录，
一个出问题的端点会把整个站点一起拖下水。

所以端点组是 Spinneret 记录以下状态的单位：

- 身份的就绪队列，以及各身份在该端点组上的冷却；
- 各身份在该端点组上的健康分与失败连击；
- 请求配额窗口；
- 熔断器的滑动窗口和状态；
- `low_watermark`（低水位）——可用身份数量低于它时触发告警。

### URI 如何映射到端点组

`Acquire` 接受显式的 `endpoint_group`，或者一个 `uri`。显式名称优先级最高；两者都不给时使用 `_default`。
`uri` 会被规范化为路径，再与该站点**加该客户端**的 URI 规则匹配——匹配器是按站点 + 客户端各建一份的，
所以 `/api/search` 在 `web` 和 `mobile` 下可以落到不同的端点组：

| 规则类型 | 模式示例 | 匹配范围 |
| --- | --- | --- |
| `exact` | `/api/search` | 仅该路径 |
| `template` | `/api/item/{id}` | 每个 `{…}` 占位符匹配一个路径段 |
| `prefix` | `/api/search` | 以它开头的任意路径 |
| `regex` | `^/api/(search\|suggest)` | 对路径求值的 Go 正则表达式 |

优先级是固定的，与规则的创建顺序无关：

1. `exact`
2. `template` —— 字面段更多者优先，其次占位符更少者，最后按 `position`
3. `prefix` —— 模式更长者优先
4. `regex` —— 按 `position`
5. `_default`

`position` 是你可以控制的同级排序依据，数值小者优先。

## 身份

**身份**是某个站点上一个可用的"身份角色"：一份 cookie、一套设备指纹、一个 token、一组签名参数，或它们的组合。
它是会被消耗、被冷却、被封禁的那个东西。

### 身份类型

身份类型就是它的结构定义。它按站点和客户端声明：

| 组成 | 含义 |
| --- | --- |
| `fields` | 载荷字段，每个字段有 `type`，以及 `required` 和 `sensitive` 标记 |
| `unique_by` | 导入时按哪些字段路径去重（最多 16 条路径） |
| `activation` | `probe`（导入为 `pending`，首次成功后激活）或 `immediate`（导入即 `active`） |
| `deliver` | 载荷如何渲染成凭据 |

字段类型有 `string`、`number`、`bool`、`cookie_map`、`json` 和 `secret_ref`。`secret_ref` 字段存放的是
命名空间内的保管库路径而不是值本身，在下发时才解析——于是一个 API key 存在密钥保管库里，而不是被复制进成千上万份
身份载荷。一个类型最多可声明 128 个字段。

```yaml
name: web_cookie
site: example-site
client: web
fields:
  cookies:    { type: cookie_map, required: true, sensitive: true }
  user_agent: { type: string }
  signature:  { type: string, sensitive: true }
unique_by: [cookies.sessionid]
activation: probe
deliver:
  cookies: "{{ cookies }}"
  cookie_header: "{{ cookies }}"
  headers:
    User-Agent: "{{ user_agent }}"
  values:
    signature: "{{ signature }}"
```

### 载荷、载荷版本、凭据

**载荷**是身份的数据本体。它以信封加密的方式静态加密（每份载荷一个 DEK，DEK 由 KEK 包裹），
并且永远不会在列表接口里返回。每次写入载荷都会产生一个新的**载荷版本**，`identities.payload_version`
指向当前版本，旧版本在被清理前一直保留——这正是一次错误的刷新可以回滚的原因。

**凭据**才是节点真正收到的东西。它是载荷经过类型的 `deliver` 模板渲染后的结果，固定分为六个段：

| 段 | 类型 | 典型用途 |
| --- | --- | --- |
| `cookies` | map | cookie 的 名称 → 值 |
| `cookie_header` | string | 同一份 cookie 预渲染为 `k1=v1; k2=v2` |
| `headers` | map | 请求头 |
| `query` | map | 查询参数 |
| `json` | 任意 JSON 值 | 请求体片段 |
| `values` | struct | 节点需要的任意带类型的值（设备参数、签名密钥） |

未使用的段返回空 map、空字符串或 null。下发模板只支持 `{{ path }}` 形式的字段占位符，其中
`cookie_map` 和 `json` 字段支持点号子键（`{{ cookies.sessionid }}`）。没有表达式、没有管道、没有函数调用：
这从根本上排除了模板注入，同时让渲染足够廉价，可以放在 Acquire 的热路径上。

### 账号

**账号**把共享同一个真实登录态的身份归为一组（`accounts.external_ref` 在站点内唯一）。它的意义在于影响面：
当一次上报说明**账号**被封了，只封其中一份 cookie 毫无意义——这个账号名下的每个身份都已失效。
因此账号级封禁会把该账号下所有成员身份移出调度，而因账号原因变更状态的成员身份会带上状态原因
`account_ban`，这样给账号解封时只会释放这些身份。

账号有自己的状态：`active`、`banned`、`disabled`，以及一个冷却时间。

## 身份状态机

一个身份在 PostgreSQL 里有一个**生命周期状态**，同时在热状态里还有一个独立的**可用性条件**。
把这两层混为一谈，是对这个模型最常见的误读。

生命周期状态：`pending`、`active`、`expired`、`banned`、`quarantined`、`disabled`、`retired`。

```text
                      导入（activation: immediate）
                ┌──────────────────────────────────────┐
                │                                      v
   导入 ────► pending ──── 首次成功 ────────────────► active ◄── 人工：启用
 (activation:    ▲           （生命周期规则）           │       │   （来自 disabled）
   probe)        │                                     │       └── 封禁到期且
                 │                                     │           ban_expiry_state: active
                 │                                     ├── 判定 auth_invalid
                 │                                     │   （动作 expire）      ──► expired
                 │                                     │
                 │                                     ├── 全局评分低于 quarantine_score
                 │                                     │   且全局样本数不少于
                 │                                     │   quarantine_min_samples ──► quarantined
                 │                                     │
                 │                                     ├── 窗口内 N 次 captcha
                 │                                     │   （动作 ban）          ──► banned
                 │                                     │
                 │                                     └── 人工：停用           ──► disabled
                 │
                 ├── 人工：解封，或封禁到期且
                 │   ban_expiry_state: pending（默认值）────────── 来自 banned
                 ├── 人工：解除隔离，或隔离到期 ───────────────── 来自 quarantined
                 ├── 人工：恢复 ────────────────────────────────── 来自 retired
                 └── 人工：激活 ──────────────────────────────►    active（跳过探测）

   任意状态 ── 人工：归档 ──► retired      （列表中隐藏，永不参与调度）
```

| 状态 | 控制台标签 | 参与调度？ | 如何进入 | 如何离开 |
| --- | --- | --- | --- | --- |
| `pending` | 待验证 | 是，但权重降低 | `activation: probe` 的导入；`unban`；`unquarantine`；`ban_expiry_state: pending` 的封禁到期；隔离到期；`restore` | 首次 `success` 上报即激活；失败仍可能导致封禁或过期 |
| `active` | 可用 | 是 | `activate`、`enable`、待验证身份首次成功、`immediate` 导入、`ban_expiry_state: active` 的封禁到期 | 任何动作规则，或人工操作 |
| `expired` | 已过期 | 否 | `auth_invalid` 判定（内置 `auth-invalid-expire` 规则）或 `expire` | 刷新载荷，或 `activate` |
| `banned` | 已封禁 | 否 | 作用域 `identity` 的 `ban` 动作，或账号被封 | 封禁结束时间（到期任务 → `ban_expiry_state`）或 `unban`（→ `pending`）。没有结束时间的封禁是永久封禁 |
| `quarantined` | 已隔离 | 否 | `quarantine` 动作（通常由健康分触发） | 隔离结束或 `unquarantine`——两者都 → `pending` |
| `disabled` | 已禁用 | 否 | 人工 `disable`，或所属账号被停用 | `enable` |
| `retired` | 已归档 | 否 | 人工 `archive` | `restore`（→ `pending`） |

除状态之外，一个 `active` 身份也可能因为热状态条件而**此刻**不可用。这些不是状态，也不会出现在状态列里：

- 处于**冷却**中，作用域可以是端点组或整个站点；
- 已被租借到 `max_concurrent_leases` 上限；
- **配额**窗口已用尽；
- 距上次使用还未满**重用间隔**；
- 所属**账号**正在冷却、被封禁或被停用；
- 绑定的**代理**不可用。

[冷却热力图](./12-observability.md)存在的意义，正是把这第二层可见化。

## 租约

**租约**是对一个身份在一个端点组上的限时占用声明。它让并发变得安全：调度器知道此刻有多少节点持有某个身份，
也能把死掉的节点手里的占用收回来。

```text
AcquireResponse
  lease.lease_id        "lse_<32 位十六进制>_<site>_<shard>"   每次上报都要带上它
  lease.identity_id     被租借的身份
  lease.identity_type   身份类型名
  lease.endpoint_group  租约所属的端点组
  lease.expires_at      不续约时的到期时间
  lease.sticky          通过 session_key 复用时为 true
  lease.probe           熔断探测或待验证身份的租约为 true
  credential            渲染后的凭据
  proxy                 轮换策略不分配代理时为 null
  hints.renew_before_ms 租约 TTL 的四分之一
```

### TTL、生命周期上限与续约

这是两个不同的限制：

| 限制 | 轮换策略字段 | 默认值 | 取值范围 | 含义 |
| --- | --- | --- | --- | --- |
| 租约 TTL | `rotation.lease_ttl` | `2m` | 5s – 30m | 一次租约在不续约情况下能存活多久 |
| 租约生命周期上限 | `rotation.max_lease_lifetime` | `30m` | 最大 24h | 反复续约后租约能达到的硬上限 |

`Renew(lease_id, extend_ms)` 从**当前时刻**起延长一个活跃租约；`extend_ms: 0` 表示使用策略的 TTL，
可接受的最大值是 `1800000`。续约永远不会缩短租约；已经到达生命周期上限的租约会以
`lease_lifetime_exceeded` 失败。续约的时机是剩余时间不足 `hints.renew_before_ms` 时，而不是固定周期。

### 归还

`Release(lease_id)` 提前结束租约，且是幂等的——如果租约已经结束，它返回 `released: false`。
通常你并不需要它：在该租约的最后一次上报里设置 `release: true`，worker 处理完就会归还，省下一次往返。

### 并发、重用与会话粘性

| 轮换策略字段 | 默认值 | 作用 |
| --- | --- | --- |
| `max_concurrent_leases` | `1` | `1` 表示独占租约：租约结束前没人能再拿到这个身份 |
| `reuse_interval` | `0s` | 同一身份两次使用之间的最小间隔 |
| `reuse_anchor` | `released` | 间隔从上次租约的 `acquired`（租借）还是 `released`（归还）起算 |
| `reuse_scope` | `endpoint_group` | 间隔在单个端点组内生效，还是跨整个 `site` 生效 |
| `quota` | `[]` | 例如 `[{limit: 60, window: 1h}]` —— 每身份每端点组的滑动窗口请求预算 |
| `warmup` | `0s`，系数 `1` | 对刚激活的身份在一段时间内按系数缩放配额 |
| `sticky.enabled` / `sticky.ttl` | `false` / `10m` | 开启后，携带相同 `session_key` 的 `Acquire` 在身份仍可用时复用同一个身份 |

会话粘性只在单个租约请求时生效；半开状态的熔断探测完全忽略粘性：探测必须落在最健康的身份上，
否则一个有问题的粘性身份会靠自己一直把端点的熔断器顶在打开状态。

独占租约同时影响同一客户端下的**其他**端点组——被 `search` 独占持有的身份对 `detail` 不可用——
归还或过期时会恢复它在这些端点组中的可用性。

### 节点持着租约挂掉时

节点侧不需要做任何事。每个实例每秒运行一次**租约回收器（lease reaper）**：取站点级锁，
按 200 条一批读取该站点已逾期的租约，把它们标记为 `expired`。如果一个租约结束时从未有上报被摄入或被处理过，
它会被标记为**abandoned（被遗弃）**。这个标记不会出现在请求明细页——请求明细只存放已处理的上报。
它体现在总览页按节点统计的**未上报租约**与**未上报比例**两列，以及指标
`spinneret_lease_reaped_total{kind="abandoned"}` 上；一批节点崩溃时，你就是从这里看出来的。

回收器同时会重新给身份评分，并恢复租约期间被推后的可用性，所以一个死掉的节点最多让你损失
该身份一个租约 TTL 的产能。

## 上报

节点上报的是**事实**，从不上报决定。分类、归因和所有状态变更都在服务端完成——这正是你可以在不重新部署节点的情况下
改规则的原因。

| 字段 | 含义 |
| --- | --- |
| `report_id` | 客户端生成的幂等键，1–64 个 `[A-Za-z0-9_.:-]` 字符；建议用 UUID |
| `lease_id` | 本次请求所用的租约 |
| `uri`、`method` | 请求路径（可带查询串）与 HTTP 方法 |
| `http_status` | 0–999；`0` 表示没有收到任何响应 |
| `business_code` | 从响应体中提取的业务状态码（如果有） |
| `error_kind` | `""`、`timeout`、`conn_reset`、`conn_refused`、`proxy_auth`、`tls`、`dns`、`other` |
| `markers` | 节点识别出的响应特征，最多 32 个，例如 `captcha_page`、`login_redirect`、`empty_list` |
| `outcome_hint` | 节点自己的判断；仅当信号策略设置了 `trust_outcome_hint` 时才采用 |
| `latency_ms`、`response_bytes` | 请求耗时与响应大小 |
| `started_at`、`finished_at` | 两者都必填；`finished_at` 不得早于 `started_at` |
| `release` | 本条上报处理完后归还租约 |

一次调用最多 500 条上报。每条上报单独校验，所以一条坏数据不会让整批被拒：响应返回 `accepted`、
`duplicated` 以及一个 `rejected` 列表，其原因为 `invalid_argument`、`lease_unknown` 或 `scope_missing`。

**标记是这个系统的扩展点。** Spinneret 对你目标站的 HTML 一无所知。当你的节点识别出"这就是被质询时出现的那个中间页"，
它附上一个像 `captcha_page` 这样的标记，再由一条信号规则把这个标记转换成判定结果。
新增一种失败形态 = 节点里加一个标记 + 策略里加一条规则，不需要改控制平面的代码。

### 幂等与投递

`report_id` 在去重窗口内被记住（`SPINNERET_REPORT_DEDUP_TTL`，默认 `1h`）。窗口内使用相同 `report_id`
的重试会被计入 `duplicated` 且不产生任何额外影响，所以节点可以安全地重试失败的 `Report` 调用。

摄入阶段只做校验、鉴权，并把上报追加到由租约 ID 决定的流分片上（`SPINNERET_REPORT_SHARDS`，默认 `16`）。
真正的处理由消费该分片的 worker 完成。每个分片维护一个"最后已应用条目"的检查点，
所以被重复投递的流条目会被识别并跳过，而不会被应用两次。

一条在租约结束后超过 `SPINNERET_LATE_REPORT_WINDOW`（默认 `10m`）才到达的上报属于**迟到上报**：
它仍然被存下来，也仍然计入熔断窗口和配额，但不更新任何健康分、样本数、失败连击和判定结果计数器，
也不规划任何动作。过时的判定结果不应该去冷却一个已经健康了十分钟的身份。

## 判定结果、归因与动作

这就是整条流水线。四个阶段，每个阶段由一种策略负责。

```text
上报 ──► 信号策略 ──► 判定结果 ──► 动作策略 ──► 动作 ──► 状态变更
        （分类）       （+ 归因）   （规则 + 计数） （+ 作用域）
```

### 1. 分类：信号策略（signal）

一组有序规则，**第一条匹配的规则胜出**。规则可以组合匹配 `http_status`、`business_code`、`error_kind`、
`markers`、`uri`（前缀或正则）、`method`、`latency_ms` 和 `response_bytes`；没有任何条件的规则匹配一切。
它产出一个 `outcome`，并可以覆盖默认的 `blame`。

十二种判定结果：

| 判定结果 | 控制台标签 | 风险？ | 必然算失败？ | 默认归因 |
| --- | --- | --- | --- | --- |
| `success` | 成功 | | | none |
| `empty` | 数据为空或截断 | | 是 | identity |
| `rate_limited` | 被限流 | 是 | 是 | both |
| `captcha` | 验证码 | 是 | 是 | identity |
| `auth_invalid` | 登录态失效 | | 是 | identity |
| `forbidden` | 访问被拒 | 是 | 是 | identity |
| `banned` | 已被封禁 | 是 | 是 | identity |
| `proxy_error` | 代理错误 | | | proxy |
| `network_error` | 网络错误 | | 仅当归因到身份时 | proxy |
| `target_error` | 目标站错误 | | | none |
| `client_error` | 客户端错误 | | | none |
| `unknown` | 未知 | | | none |

"风险"判定是熔断器统计的对象；"失败"判定是让身份失败连击递增的对象。

**归因**决定谁付出代价：身份、代理、两者都算，或者谁都不算。它是阻止一个坏代理毁掉上百个好身份的关键。
交叉归因会自动修正它：在默认 10 分钟的窗口内，如果某个代理上至少 3 个不同身份出现了风险判定，
而该身份接触过的不同代理少于 3 个，归因转移到代理；如果某个身份在至少 3 个不同代理上都失败，
则身份也被计入归因。

内置默认信号策略按顺序分类：代理认证 / 连接被拒 → `proxy_error`；超时 / 连接重置 / TLS / DNS →
`network_error`；标记 `captcha_page` → `captcha`；标记 `login_redirect` → `auth_invalid`；
429 → `rate_limited`；≥500 → `target_error`；200 且带标记 `empty_list` → `empty`；
400 → `client_error`；401 → `auth_invalid`；403 → `forbidden`；2xx → `success`。

### 2. 处置：动作策略（action）

所有 `when` 匹配的规则都会被求值，然后**每个对象上最严重的动作胜出**——身份、账号、代理各自最多一个动作。
规则的 `when` 接受一组判定结果，以及可选的 `count` 条件（滑动窗口 `within` 内至少 `gte` 次），
该计数针对规则作用域所指的对象。

四种动作及各自允许的作用域：

| 动作 | 允许的作用域 | 效果 |
| --- | --- | --- |
| `cooldown` | `identity_endpoint`、`identity_site`、`identity`、`account`、`proxy_site`、`proxy` | 让对象在某个时间点之前不可用；状态不变 |
| `quarantine` | `identity`、`proxy` | 隔离待审查；`duration` 结束后解除（身份 → `pending`） |
| `ban` | `identity`、`account`、`proxy` | 在封禁结束前移出调度；`duration: permanent` 表示永不结束 |
| `expire` | `identity` | 把凭据标记为失效，交由刷新流程替换 |

另有 `activate` 动作，但它只由生命周期规划（`pending` 身份上报 `success` 时），不能写在规则里。

| 作用域 | 控制台标签 | 影响面 |
| --- | --- | --- |
| `identity_endpoint` | 身份 × 端点组 | 一个身份，一个端点组 |
| `identity_site` | 身份 × 站点 | 一个身份，该站点的所有端点组 |
| `identity` | 身份 | 一个身份，全部范围 |
| `account` | 账号 | 该账号下所有身份 |
| `proxy_site` | 代理 × 站点 | 一个代理，一个站点 |
| `proxy` | 代理（全部站点） | 一个代理，全部范围 |

一次冷却的时长是 `min(base × multiplier^min(streak − 1, max_exponent), max) × jitter`，
其中 `streak` 是该对象当前的失败连击数，`jitter` 取自 `[0.8, 1.2]`。指数是 `streak − 1`，
所以一轮连击的第一次冷却就是 `base` 本身。连击在 `failure_reset_after`（默认 `1h`）内没有新失败时归零，
一次成功会把它减半。

冷却默认是**固定时长**的，因为 `multiplier` 的默认值就是 `1`。要让它变成指数式，把 `multiplier` 设成
大于 `1` 的值，上界由 `max_exponent`（默认 `10`）和 `max`（默认 `24h`）控制。内置的 `default-action`
策略只在 `rate_limited` 和 `captcha` 两条规则上用了 `multiplier: 2`，其余冷却规则都是固定时长。

临时封禁会沿**升级阶梯（escalation）**攀升，依据是对象近期被封禁的频次。内置默认：
7 天内 2 次封禁 → 72h，30 天内 3 次封禁 → 永久。

封禁结束时，身份回到 `ban_expiry_state` 指定的状态——默认是 `pending`，即必须靠一次成功的探测重新赢回资格；
如果你信任它，也可以设为 `active`。到期任务读取的是该身份所属 站点 + 客户端 的 `_default` 端点组上解析出的
动作策略里的这个字段，而不是当初下发封禁的那条策略，所以把它写在某个端点组级绑定上对封禁到期没有任何影响。

`mode: shadow` 的动作策略只规划、不执行：状态事件以 `shadow: true` 记录，让你精确看到这条策略**本来会**做什么。
在发布一条会封禁东西的规则之前，先用影子模式。

## 健康分

每个身份在热状态里带两个指数加权评分：一个按端点组，一个全局（该身份在整个站点上的）。
评分是 0–100 的数值，附带一个样本数。

每条被处理的上报按两步更新相关评分：

```text
衰减：score = baseline + (score - baseline) * exp(-(now - 上次更新) / tau)
更新：score = alpha * 观测值 + (1 - alpha) * score
```

默认值：`alpha: 0.1`、`baseline: 70`、`tau: 6h`。衰减让久远的事故不再影响判断：长期未被使用的身份会
漂回基线，而不是被永久判死。

观测值由判定结果决定。身份观测值（可在策略的 `health.observations` 中覆盖）：

| 判定结果 | 观测值 | 生效条件 |
| --- | --- | --- |
| `success` | 100 | 始终生效 |
| `empty` | 60 | 归因包含身份时 |
| `network_error` | 50 | 归因包含身份时 |
| `rate_limited` | 30 | 归因包含身份时 |
| `forbidden` | 10 | 归因包含身份时 |
| `captcha` | 0 | 归因包含身份时 |

代理有自己的固定表：`success` 100（始终生效）、`proxy_error` 0、`network_error` 40、`rate_limited` 30，
后三者仅在归因包含代理时生效。

健康分以两种方式反馈到轮换上。

1. **选择。** 默认策略 `weighted_random` 按候选者评分的平方加权（评分先夹到 `[5, 100]`），
   所以评分 100 被选中的概率是评分 50 的四倍、是评分 5 的 400 倍。一个正在恶化的身份是逐渐淡出流量，
   而不是被一刀切断。`best_health` 直接选评分最高者，半开熔断探测用的就是它；
   `least_recently_used` 和 `round_robin` 完全不看评分。
2. **评分驱动的动作。** 这是两个彼此独立的检查，并且都只在本次上报确实影响到该身份时才执行——
   归因包含身份，或判定结果属于失败。第一个检查读的是 身份 × 端点组 的评分：低于
   `health.endpoint_low_score`（默认 `15`）且**该端点组上的**样本数不少于
   `endpoint_low_min_samples`（默认 `10`）时，该身份在这个端点组上被冷却
   `endpoint_low_cooldown`（默认 `6h`）——如果那里已经有一个更长的冷却在跑，这次就跳过。
   第二个检查读的是该身份的**全局**评分，而不是端点组上的评分：低于
   `health.quarantine_score`（默认 `20`）且**全局**样本数不少于 `quarantine_min_samples`（默认 `10`）时，
   它被隔离 `quarantine_duration`（默认 `24h`）。

最小样本数的存在，正是为了防止两次倒霉的请求就把一个好身份隔离掉。

## 熔断器

冷却保护的是**身份**；熔断器保护的是**目标站**——以及通过它保护你的整个身份池。当一个端点组开始对所有请求
返回验证码时，继续发请求拿不到数据，只会把你手里每一个身份一个接一个烧掉。熔断器的做法是直接掐断流量。

熔断器属于一个端点组，统计一个滑动窗口内的上报（默认 `60s`，切成 `12` 个 5 秒的桶）。

```text
          窗口内请求数 >= min_requests 且满足任一触发条件
 closed ──────────────────────────────────────────────────────► open
   ▲                                                             │
   │                                                             │ open_duration 到期
   │  探测样本数 >= close_min_samples                            │ （由下一次 Acquire 推动）
   │  且探测成功率 >= close_success_ratio_gte                    v
   └──────────────────────────────────  half_open  ◄─────────────┘
                                            │
                                            │ 探测样本数 >= close_min_samples
                                            │ 且探测成功率 < close_success_ratio_gte
                                            └────────────────────► open（更长，上限 max_open_duration）
```

| 状态 | 控制台标签 | `Acquire` 的行为 |
| --- | --- | --- |
| `closed` | 关闭 | 正常服务 |
| `open` | 打开 | 立即以 `circuit_open` 失败，并给出 `Spinneret-Retry-After-Ms` 提示 |
| `half_open` | 半开 | 每 10 秒窗口内最多发放 `probe_leases_per_10s`（默认 `5`）个探测租约，其余请求得到 `circuit_open` |

触发条件——满足任意一条即打开熔断；设为 `0` 表示禁用该条件。窗口内上报数不足
`min_requests`（默认 `50`）时，所有条件都不生效；而且触发条件只在熔断器处于 `closed` 时才被求值：
`half_open` 状态的去向完全由探测结果决定。

| 条件 | 默认值 | 含义 |
| --- | --- | --- |
| `trip.risk_ratio_gte` | `0.4` | 窗口内 风险判定 / 总上报数 |
| `trip.distinct_captcha_identities_gte` | `10` | 出现过验证码的不同身份个数 |
| `trip.success_ratio_lte` | `0.2` | 成功率低于该值即打开 |

打开状态持续 `open_duration`（默认 `2m`）。此后第一次 `Acquire` 会把它推进到 `half_open` 并取走一个探测。
如果在 `reset_open_count_after`（默认 `30m`）内反复打开而没有平静期，打开时长会逐次延长，
上限为 `max_open_duration`（默认 `1h`）。**探测租约**在响应里标记为 `probe: true`；
它的上报决定状态迁移，并且不受"熔断打开期间抑制动作"的限制。

由于熔断器的结论本质上是"这不是身份们的错"，打开熔断时还会**回滚它造成的近期冷却**：
`revert_recent_cooldowns: endpoint`（默认）归还打开的那个端点组上的 身份 × 端点组 冷却，
`all` 在此之外再归还这些身份的站点级冷却，`none` 什么都不做。被回滚的只有冷却——封禁、隔离和失效一律保留。

在非探测租约的熔断器实际处于打开状态时被处理的上报会被**抑制（suppressed）**，其门控与迟到上报完全一样：
上报仍然被存下来、仍然计入熔断窗口和配额，但不更新任何健康分、样本数、失败连击和判定结果计数器，
也不规划任何动作。请求明细页会在这一行上写明"熔断器处于打开状态，未更新健康度也未执行动作"。
否则，熔断触发前你已经发出去的那批请求，会继续为一个根本不属于身份的故障惩罚它们。

评估巡检每 5 秒在每个实例上运行一次，评估近期有活动的端点组，外加所有熔断器不处于关闭状态的端点组——
所以即使没有流量到达，熔断器也会自己关闭。

**暂停站点**是同一思路的人工版本：该站点的所有端点组上，`Acquire` 都以 `site_paused` 失败，
并给出 30 秒的重试提示。

## 代理池

**代理池**属于命名空间而不是站点，所以一个池服务团队运营的所有站点。每个代理带有协议
（`http`、`https`、`socks5`）、主机、端口、类型（`datacenter`、`residential`、`mobile`、`tunnel`）、
地区与城市、供应商、标签、`max_concurrency` 以及可选的会话模板。含凭据的完整 URL 静态加密存储，
明文只保留一个不含凭据的展示 URL 和一个用户名提示。

由轮换策略决定代理如何选取：

| `proxy.mode` | 行为 |
| --- | --- |
| `none` | 不分配代理；响应的 `proxy` 字段为 null |
| `pool` | 每个租约从池中选一个代理，按 `kinds`、`providers`、`regions`、`tags` 过滤 |
| `bind_identity` | 每个身份跨租约固定使用一个代理（记录在 `proxy_bindings`），只在绑定的代理不可用时重新绑定，并受 `rebind_tolerance`（默认 `5m`）和 `max_rebinds_per_day`（默认 `3`）限制 |
| `region_match` | 与 `pool` 相同，但代理的地区必须等于身份的地区。`region_match: true` 标记可把同样的限制加到 `pool` 和 `bind_identity` 上 |

池内选择先对代理的健康分做衰减，再按 `max(score, 5)²` 加权——这里只夹下界，与身份选择夹到
`[5, 100]` 并不相同——候选范围限定为 `active`、未处于冷却、且并发未达 `max_concurrency` 的代理。当没有任何代理能服务这个租约时，
`Acquire` 以 `no_proxy_available` 失败，而不会发出一个"裸奔"的身份。

**代理与身份共同承担责任。** 两者都记录在租约上，所以上报回来时，由归因决定谁付代价：

- `blame: proxy` → 代理健康分下降，代理作用域的规则可以冷却或封禁它；身份不受影响。
- `blame: identity` → 身份付代价；代理不受影响。
- `blame: both`（`rate_limited` 的默认值）→ 两者都付代价。
- 交叉归因可以按上文规则自动转移归因。

代理拥有与身份相同的冷却粒度：`proxy_site` 只冷却该代理在一个站点上的使用（被某个目标站封掉的代理，
对另一个目标站通常仍然好用），而 `proxy` 在所有站点上冷却或封禁它。后台健康检查按计划探测代理，
维护同样的 EWMA 评分，连续检查失败会把代理标记为 `dead`（不可用）。

## 配置与密钥

节点在运行时从 Spinneret 获取自己的配置和密钥。理由与它在运行时获取身份的理由完全相同：
烧进镜像里的值只能靠一次部署来改变，而当目标站行为突变时，一次部署所需的那几分钟你恰恰没有。

**配置项**存放在命名空间内的配置分组里，格式为 `json`、`yaml` 或 `text`。只有已发布版本会下发给节点。
每次发布和回滚都会递增版本号，且同一 命名空间/分组/键 的版本号永不重复。节点用 `GetConfig` 读一项，
用 `BatchGetConfig` 读多项，用 `WatchConfig` 订阅：这是一个长轮询，如果有配置项的版本与节点持有的版本不同就立即返回，
否则最多等待 `timeout_ms`（默认 30000，最大 60000）后返回空列表。节点持有版本 0 的配置项，
会在它有了已发布版本时立刻拿到。这就是一次配置变更如何在数秒内到达整个节点集群，
而不需要任何节点轮询空转。

保留的只读分组 `_runtime` 暴露两份由 Spinneret 自己维护的文档：`breakers`（所有端点组的当前熔断状态）
和 `site_switches`（哪些站点被暂停）。节点可以订阅它们，避免发出自己已经知道会被拒绝的请求。

**密钥**存放在命名空间内的保管库路径下，受信封加密保护：每个密钥版本用自己的 DEK 封装，DEK 再由 KEK 包裹。
节点用 `GetSecret(path, version)` 读取（`version` 为 `0` 表示当前版本），需要一条对
`"<namespace>/<path>"` 生效的 `secret:read:<glob>` 权限范围。每一次读取都会写入审计日志。

这两个系统可以组合：配置项内容里可以包含 `${secret:...}` 引用，服务端会在下发前解析它们，
并把内容曾包含引用的配置项标记为 `has_secret_refs: true`。节点不得以明文持久化这类内容。
身份载荷通过 `secret_ref` 字段实现同样的组合。

## 策略与绑定层级

四种策略，各回答一个问题：

| 类型 | 控制台标签 | 它回答的问题 |
| --- | --- | --- |
| `rotation` | 轮换 | 这次请求拿到哪个身份、哪个代理？ |
| `signal` | 识别 | 这条上报到底意味着什么？ |
| `action` | 处置 | 这对身份、账号或代理意味着什么代价？ |
| `breaker` | 熔断 | 什么时候停止向这个端点组发请求？ |

策略以 YAML 编写，带版本、可发布、可回滚。信号策略和动作策略可以 `extends` 一个父策略
（链长最多 5，拒绝成环），于是团队可以维护一份统一策略，再按站点覆盖少量规则。

### 解析

每种策略针对请求所在的端点组独立解析，最具体的绑定胜出：

```text
端点组  >  客户端  >  站点  >  命名空间  >  内置默认
```

- 端点组级绑定必须指定端点组，并且它若指定了站点和客户端，也必须匹配；
- 客户端级绑定指定站点和客户端，不指定端点组；
- 站点级绑定只指定站点；
- 命名空间级绑定不指定站点、客户端和端点组；
- 指定了客户端或端点组但没有指定站点的绑定永远不会匹配；
- 若多条绑定处于同一胜出层级，第一条胜出；
- 若什么都没匹配上，则使用内置的 `default-rotation`、`default-signal`、`default-action` 或
  `default-breaker`。

### 一个完整示例

命名空间 `prod` 中的绑定：

| # | 类型 | 站点 | 客户端 | 端点组 | 策略 |
| --- | --- | --- | --- | --- | --- |
| 1 | `action` | — | — | — | `house-action` |
| 2 | `action` | `example-site` | — | — | `site-action` |
| 3 | `action` | `example-site` | `web` | `search` | `search-action` |
| 4 | `rotation` | `example-site` | `web` | — | `web-rotation` |

请求 `Acquire(site: example-site, client: web, uri: /api/search?q=x)` 匹配到 `search` 端点组，解析结果：

- **动作** → `search-action`，层级 `endpoint_group`（第 3 行胜过第 2、1 行）；
- **轮换** → `web-rotation`，层级 `client`（第 4 行）；
- **信号** → 完全没有绑定 → 内置 `default-signal`，层级 `builtin`；
- **熔断** → 没有绑定 → 内置 `default-breaker`，层级 `builtin`。

同一个调用如果 `uri: /api/item/123` 并匹配到 `detail` 端点组，动作策略会解析为 `site-action`，
因为第 3 行只绑定了 `search`。控制台在端点组上直接展示解析出的策略及其层级，你不必手工推演。

各类型策略的 YAML、草稿、版本对比与规则调试器见[策略](./08-policies.md)。

## 一次请求的完整流程

这是整个系统的一条完整轨迹。一个节点抓取 `example-site` 上的 `/api/search?q=shoes`，客户端为 `web`。

1. **节点调用 `Acquire`**，参数 `site: example-site`、`client: web`、`uri: /api/search?q=shoes`、
   `wait_ms: 500`，携带一个 API 令牌。API 层验证令牌、解析它所属的命名空间，并检查该站点上的
   `lease:acquire` 权限。
   *状态变更：* 暂无。

2. **调度器解析目标。** 在命名空间目录中查到站点，并检查 `paused`（被暂停的站点此刻就以 `site_paused`
   失败并给出 30 秒重试提示）。URI 规范化为 `/api/search`，与该站点 + 客户端（`example-site` + `web`）
   的 URI 规则匹配，选出 `search` 端点组。
   该端点组的轮换策略通过绑定层级解析出来。
   *状态变更：* 暂无。

3. **熔断闸门。** 调度器读取 `search` 的熔断器。关闭 → 继续。打开且未到期 → 返回 `circuit_open`
   并附上剩余毫秒数。打开且已到期 → 推进到 `half_open`，本次调用作为探测。半开且探测配额已用尽 →
   返回 `circuit_open`。
   *状态变更：* 可能发生 `closed`/`open` → `half_open`，以及本 10 秒窗口的探测计数。

4. **身份选择。** 在一段原子 Lua 脚本里，调度器从端点组的就绪队列中抽样最多 `candidate_sample`
   （默认 32）个身份，队列的分值就是每个身份变为可用的时间点。候选者若不是 `active`/`pending`、
   仍在冷却、已达 `max_concurrent_leases`、处在重用间隔内、配额已用尽、绑定了不可用的代理，
   或所属账号被封禁 / 停用 / 冷却，就会被剔除或推后。配置的策略在存活的候选者中挑选——
   `weighted_random` 按评分平方加权，`best_health` 用于探测。如果请求带了 `session_key` 且粘性已开启，
   会先尝试该会话上次使用的身份。
   *状态变更：* 被过滤掉的候选者在就绪队列中重新打分，使下次调用能低成本地跳过它们。

5. **代理分配。** 依据 `proxy.mode`，脚本可能不分配代理、从池中选一个（按类型、供应商、地区和标签过滤，
   按评分平方加权）、复用身份已绑定的代理，或绑定一个新代理。如果没有任何代理能服务这个租约，
   调用会在 `wait_ms` 预算内重试（50/100/150/200 毫秒退避）或以 `no_proxy_available` 失败。
   *状态变更：* 代理的活跃租约计数；`bind_identity` 模式下可能新增或改写一条 `proxy_bindings`
   记录及其当日重绑计数。

6. **写入租约。** 创建租约哈希，记录身份、代理、端点组和到期时间（`now + lease_ttl`），
   把租约 ID 加入站点的到期集合，把身份的可用时间推到租约之后（并顺延重用间隔），推进配额窗口。
   如果在 `wait_ms` 预算内都找不到候选者，调用以 `no_identity_available` 失败。
   *状态变更：* 一条新租约；身份的最近使用时间与可用性；配额计数器。

7. **渲染并返回凭据。** 解密身份载荷，把所有 `secret_ref` 字段从密钥保管库解析出来，
   再用类型的 `deliver` 模板渲染成凭据。节点收到 `lease`、`credential`、`proxy` 和 `hints`。
   *状态变更：* 一条 `lease_events` 记录、租借统计与指标。此时还没有请求明细里的行——那一行要到第 14 步、
   上报被处理之后才出现。

8. **节点发出请求**，用给定的凭据经由给定的代理访问目标站。Spinneret 不参与这一步。
   如果工作时长超过 TTL，节点在剩余时间不足 `hints.renew_before_ms` 时调用 `Renew`。

9. **节点调用 `Report`**，带上新的 `report_id`、`lease_id`、URI 与方法、HTTP 状态码、
   识别到的标记、耗时、字节数、起止时间戳，以及 `release: true`。摄入阶段校验上报、
   检查该租约站点上的 `report:write` 权限、如果该 `report_id` 在去重窗口内出现过就当作重复丢弃，
   然后把它追加到由租约 ID 决定的流分片上。调用立即返回。
   *状态变更：* 一条流条目；去重键。

10. **一个 worker 取走这条条目。** 它解析出站点、租约和端点组，然后用解析出的信号策略对上报分类：
    第一条匹配的规则给出判定结果和归因。假设节点附上了 `captcha_page`——判定结果 `captcha`，
    归因 `identity`。
    *状态变更：* 暂无。

11. **原子地更新热状态。** 分片检查点前移（于是重复投递的条目会被跳过）。熔断器滑动窗口的当前桶把这次请求
    计入总数和风险数，把该身份加入窗口的"出现过验证码的不同身份"集合，配额窗口同时推进。接着给这条上报定性：
    熔断器实际处于打开状态且本次不是探测 → **suppressed（已抑制）**；在租约结束后很久才到达 →
    **late（迟到）**；两者都不是则是一条普通上报。只有普通上报才会继续走评分这一段——身份在该端点组上的
    健康分和全局健康分先衰减再以观测值 0 更新，样本数递增，失败连击加一，如果归因包含代理则代理评分同样更新，
    判定结果计数器和交叉归因集合前移。两种标记任一都会让这条上报就此终止，第 12 步也随之跳过。
    *状态变更：* 熔断窗口和配额总是更新；健康分、连击数、计数器只对普通上报更新。

12. **求值动作策略**，输入是判定结果、归因、身份状态以及刚刚读到的各项计数。内置默认策略针对 `captcha`
    规划一个作用域 `identity_site`、基数 `30m`、倍数 2 的 `cooldown`；如果这是 24 小时内第三次验证码，
    还会规划一个作用域 `identity`、时长 12 小时的 `ban`。每个对象上最严重的动作胜出，
    所以对这个身份来说封禁取代冷却。如果策略的封禁升级阶梯命中，12 小时会变成 72 小时或永久。
    *状态变更：* 暂无——这一步只做规划。

13. **执行器应用这个计划。** 在 `enforce` 模式下，身份在热状态中立即被封禁，PostgreSQL 中的行随后异步落库，
    并记录一条状态事件（`from_state: active`、`to_state: banned`、`action: ban`，
    附带导致它的策略、版本、规则、`report_id` 和 `lease_id`）。在 `shadow` 模式下什么都不执行，
    事件以 `shadow: true` 记录。这条状态事件会出现在风险事件页、身份详情时间线和通知流水线上。
    *状态变更：* 身份的状态与可用性；一条状态事件；告警。

14. **归还租约**（因为上报要求归还），并通知熔断器这个端点组出现了一次风险判定。
    该请求被记入请求明细和站点级统计。
    *状态变更：* 租约结束；身份的活跃租约数与代理的并发数各减一。

15. **5 秒之内，熔断巡检评估 `search` 端点组。** 如果窗口内已有至少 50 条上报且风险比例越过 0.4，
    或者已有 10 个不同身份出现过验证码，熔断器打开 2 分钟、回滚它在该端点组上造成的冷却，
    并发布一条状态迁移事件。第 13 步那次封禁会被保留：回滚的只有冷却。
    此后所有针对 `search` 的 `Acquire` 都以 `circuit_open` 失败，
    直到打开期结束——而打开期之后节点的下一次 `Acquire` 就成为那个决定端点是否恢复的探测。

整个过程中，没有任何人部署过任何东西。
