## 它解决的问题

一个 Spinneret 节点只需要配置两样东西：服务端地址和 API 令牌。其余一切——调用哪些端点、以什么
速率运行、用哪个解析变体、当前的签名参数是什么——都在运行时从服务端取得。

这是刻意的设计。如果一个设置写在节点的环境变量文件或容器镜像里，改一次就要重新部署全部节点；
在滚动发布的这段时间里，集群同时跑着两个版本的设置；事后也没人说得清凌晨三点生效的到底是哪个值。
配置中心把这些换成：一个统一的编辑入口、每次发布产生一个不可变版本、每次变更留一条审计记录，
以及一条远不到一秒就能把变更送到每个订阅节点的下发通道。

它不是什么：它不是服务端自身的配置。`SPINNERET_*` 变量配置的是 Spinneret 服务进程，那部分见
[配置参考](./03-configuration.md)。配置中心下发的是**你的**节点配置，而且 Spinneret 从不解释它的
内容——对服务端来说，那只是一段经过校验的 JSON、YAML 或文本。

## 配置项、分组与键

一个**配置项**由三段名字定位：

```
<命名空间> / <分组> / <键>
```

| 组成 | 含义 | 规则 |
| --- | --- | --- |
| 命名空间 | 配置项所属的隔离单元。节点的令牌绑定到唯一一个命名空间。 | 由令牌决定；请求里可以显式写出，但必须一致。 |
| 分组 | 相当于目录。既用于组织结构，也用于把令牌限制在配置的一部分上。 | `^[a-zA-Z0-9][a-zA-Z0-9_.-]{0,63}$`。以 `_` 开头的名字为系统保留。 |
| 键 | 分组内的配置项名。 | `^[a-zA-Z0-9][a-zA-Z0-9_./-]{0,127}$`。允许斜杠，所以键可以长得像一条路径。 |

节点请求的就是「分组/键」这一对名字，删除后再重建也不会变。配置项内部另有一个 `cfg_…` 形式的
ID，管理 API 会用到；节点永远看不到它。

一种可用的组织方式：

```text
crawler/search.json        search 端点的参数
crawler/detail.json        detail 端点的参数
crawler/rate.yaml          按站点的并发与节奏
partner-api/client.json    partner 集成的设置
_runtime/breakers          系统维护，只读
_runtime/site_switches     系统维护，只读
```

请像规划令牌权限范围那样规划分组，因为分组本来就是为此存在的：一个只读 `crawler/*` 的节点，
拿到权限范围为 `config:read:crawler*` 的令牌，在物理上就读不到 `partner-api/*`。

## 格式与校验

每个配置项有三种格式之一，创建后不可更改：

| 格式 | 存储形式 | 保存和发布时的校验 | 是否可绑定 JSON Schema |
| --- | --- | --- | --- |
| `json` | UTF-8 文本 | 必须能解析为 JSON | 可以 |
| `yaml` | UTF-8 文本 | 流中的每个文档都必须能解析为 YAML | 可以 |
| `text` | UTF-8 文本 | 除大小和编码外不做校验 | 不可以 |

内容必须是合法 UTF-8，不能含 NUL 字节，且不能超过 **4 MiB**。

### JSON Schema

`json` 和 `yaml` 配置项可以绑定一份不超过 1 MiB 的 **JSON Schema（draft 2020-12）**。服务端会编译
它，并在每次保存草稿和每次发布版本时用它校验内容。对 YAML，流中的每个文档会分别转成 JSON 再校验；
空流按一个 `null` 文档处理。

外部 `$ref` 一律拒绝——Schema 不能让服务端去读本地文件或访问网络。校验失败返回
`invalid_argument`，最多列出 20 条去重后的位置与原因，编辑器因此能指出具体是哪个字段出错。

Schema 是防止错误发布最便宜的一道闸。给那些会被节点解析成结构体的配置项加一份 Schema，只花几分钟，
却能把一次全集群崩溃变成一次被拒绝的发布。

```json
{
  "type": "object",
  "required": ["concurrency", "timeout_ms"],
  "properties": {
    "concurrency": { "type": "integer", "minimum": 1, "maximum": 64 },
    "timeout_ms":  { "type": "integer", "minimum": 100, "maximum": 30000 },
    "variant":     { "enum": ["a", "b"] }
  },
  "additionalProperties": false
}
```

## 草稿、版本、发布与回滚

每个配置项有且只有一份可变的**草稿**，以及一串不可变的**已发布版本**。节点只会看到已发布版本。

```
编辑  →  草稿（会校验，节点看不到）
      →  发布  →  版本 N（不可变，下发给节点）
      →  回滚  →  版本 N+1，内容取自某个旧版本
```

### 保存草稿

`SaveConfigDraft` 保存内容，也可以顺带更新 Schema 或描述，需要 `config:write`。草稿的校验和已发布
内容完全一样——语法、Schema、密钥引用的**语法**——但被引用的密钥此时还不需要存在，所以你可以在密钥
创建之前就把配置变更准备好。

如果草稿内容和当前已发布版本逐字节相同，它不会被保存而是被清除；控制台会提示「内容与已发布版本
一致，草稿已清除」。

### 发布

`PublishConfig` 需要 `config:publish`。它在数据库事务内重新校验草稿，这一次还会检查**每一个被引用
的密钥、以及每一个被固定的密钥版本都在该命名空间中存在**。缺少任何一个，发布会以
`failed_precondition` 失败，并列出找不到的那些引用——配置绝不会以「节点解析不出来」的状态被发布
出去。

发布成功后草稿被清除，写入一个新版本，配置项的 `current_version` 指向它。

`expected_version` 提供乐观并发控制：把它设成你当时看到的版本号，如果期间别人先发布了，本次发布会
以 `conflict` 失败。设为 `0` 表示跳过检查。

### 版本号

版本从 1 开始，**每次发布和每次回滚**都加一。在同一个「命名空间/分组/键」下版本号永不重复。删除
配置项时会把它的最后一个版本记为下限，同名配置项再次创建时从该下限之上继续，而不是从 1 重新开始。
这一点很重要，因为节点只用分组、键和版本号来识别内容：重复的版本号会让节点以为自己已经持有一份
从未见过的内容。

### 回滚

`RollbackConfig` 接收一个旧版本号，把**它的内容**重新发布为一个新版本，并在 `source_version` 中记下
内容来自哪里。历史保持线性——什么都不会被改写或删除，版本历史里会显示「回滚自 v7」。

有两点值得知道：

- 内容会用配置项**当前**的 Schema 重新校验。如果 v7 发布之后 Schema 被收紧了，回滚到 v7 完全可能
  失败。先放宽或移除 Schema，或者回滚到一个能通过校验的版本。
- 回滚**不会**动草稿。如果配置项上挂着一份无关的草稿，回滚之后它还在那里，等着下一个按下「发布」
  的人把它发出去。

回滚到当前版本本身会以 `failed_precondition` 失败。

### 删除

`DeleteConfigItem` 需要 `config:publish`，会永久删除配置项及其所有版本。此后节点读取它会得到
`not_found`；删除**不会**唤醒订阅者，它们会继续持有最后拿到的那份内容，直到本次长轮询超时后重新
发起轮询。所以删除一个仍有节点依赖的配置项，是一种缓慢而无声的故障——更好的做法是发布一个安全值。

### 谁改了什么

每个配置项记录最后保存草稿的操作者（`draft_updated_by`）和发布当前版本的操作者（`published_by`），
形式为 `user:<id>` 或 `token:<id>`，都带时间戳。每个已发布版本另外保存自己的 `published_by`、
`published_at` 和自由文本 `comment`。

在此之外，审计日志记录 `config.create`、`config.draft.save`、`config.publish`、`config.rollback`
和 `config.delete`，以及节点被拒绝读取某个被引用密钥时的一条 denied 的 `config.read`。
**配置内容永远不会写入审计日志。**

## 密钥引用

配置内容可以引用[密钥保管库](./10-secrets.md)中的密钥，而不是把值嵌进去：

```text
${secret:<path>}            密钥的当前版本
${secret:<path>#<version>}  固定到某个版本
```

路径相对于配置项所在的命名空间，必须匹配 `^[a-z0-9][a-z0-9_./-]{0,255}$`，且不能有空段、`.` 或
`..` 段。固定版本必须是不带前导零的正整数。单个配置项中最多允许 **100 个互不相同的引用**。

没有转义语法：内容中**每一处** `${secret:` 都必须构成一个合法引用，否则保存会被拒绝，返回
`invalid_argument` 并指出字节偏移。如果你需要这段字面文本，那就不要写它。

### 节点如何拿到值

| 读取方 | 看到的内容 |
| --- | --- |
| 控制台与 `ConfigAdminService` | 原始内容，引用按原文显示，从不解析 |
| 通过 `ConfigService` 读取的节点 | 每个引用都被替换成密钥值后的内容 |

替换是每次请求进行一次，并且以调用方的身份进行：

1. 服务端收集该已发布版本中互不相同的引用（版本首次加载时扫描一次，之后与内容一起缓存）。
2. 对每个引用，**以节点的身份**读取密钥，用途标记为 `config:<group>/<key>`。能否读到由节点自己的
   `secret:read:<namespace>/<path glob>` 权限范围决定，并且这次读取会像任何一次密钥读取一样写入
   密钥审计记录。
3. 对 `json` 配置项，值在替换前会做 JSON 字符串转义，所以含引号或反斜杠的密钥不会破坏文档结构。
   `yaml` 和 `text` 直接插入原值。

如果节点的令牌覆盖不到其中某个路径，**整个请求**会以 `permission_denied` 失败（令牌对应的 reason 是
`scope_missing`）——绝不会返回一份带窟窿的半成品——并且这次拒绝会以 `config.read` / `denied` 记入
审计。如果某个被引用的密钥在发布之后消失了，请求以 `failed_precondition` 失败。

### `has_secret_refs` 标志

任何下发的配置项，只要其已发布内容中含有引用，就会带上 `has_secret_refs: true`。客户端不得把这类
内容以明文持久化。两个 SDK 都遵守这一点：Go 和 Python 的配置订阅器不会把被服务端标记的配置项写入
本地快照，并会删除它此前的旧快照。Python 订阅器也可以改为加密保存密钥快照
（`cache_secrets=True`，密钥由 API 令牌派生）；两个 SDK 还都接受 `treat_as_secret` /
`TreatAsSecret` 断言，用于那些直接嵌入敏感值而非使用引用的配置项。

```json
{
  "endpoint": "https://target.example/search",
  "api_key": "${secret:signing/api_key}",
  "legacy_key": "${secret:signing/api_key#3}"
}
```

## 节点侧协议

`ConfigService` 上共三个 RPC，都要求对所涉及的每个分组具备 `config:read`：

| RPC | 过程路径 | 行为 |
| --- | --- | --- |
| `GetConfig` | `/spinneret.v1.ConfigService/GetConfig` | 单个配置项；不存在或从未发布时返回 `not_found` |
| `BatchGetConfig` | `/spinneret.v1.ConfigService/BatchGetConfig` | 1–200 个配置项；不存在或未发布的进入 `missing`，不会使整个调用失败 |
| `WatchConfig` | `/spinneret.v1.ConfigService/WatchConfig` | 1–200 个配置项；长轮询等待变更 |

传输方式、认证和 JSON 编码见[节点 API 参考](./13-node-api.md)；下面的内容对三者都适用。

下发的 `ConfigItem` 包含 `namespace`、`group`、`key`、`format`、`version`、`content`、
`updated_at` 和 `has_secret_refs`。

### 版本令牌

`version` 就是节点需要维护的全部协议状态。它是一个普通的 `int32`，在该配置项每次发布和回滚时递增，
且永不重复。

`WatchConfig` 对每个配置项带上节点当前持有的版本：

- `version: 0` 表示「我什么都没有」——该配置项一旦有了已发布版本就会被返回。
- 其他值表示「我持有这个版本」——一旦已发布版本与它**不同**就会被返回。

比较的是「不同」，而不是「更大」。正因如此回滚才能送达节点：回滚固然会产生更大的版本号，但任何
发布都会；而一个被删除后重建的配置项，也会带着它的新版本号被下发。

### 长轮询语义

```
POST /spinneret.v1.ConfigService/WatchConfig
{
  "items": [
    {"group": "crawler", "key": "search.json", "version": 12},
    {"group": "crawler", "key": "rate.yaml",   "version": 4}
  ],
  "timeout_ms": 30000
}
```

- 如果已经有配置项不一致，调用立刻返回这些变更项。
- 否则阻塞等待。`timeout_ms: 0` 选用服务端默认的 **30 000 ms**；可接受的最大值是 **60 000 ms**，
  服务端无论如何都会把等待时间截断在 60 秒；客户端更短的截止时间会进一步缩短它。
- 超时时返回一个空的 `items` 列表。这是正常且预期的结果，不是错误。带着同样的版本号再轮询一次。
- 响应**只**包含发生变化的配置项。没变的、被删除的、以及从未发布过的都不会出现，而且被删除或未发布
  的配置项不会结束本次轮询。

有两个细节保证了多实例部署下的正确性：

- **节点绝不会被推回旧版本。** 如果节点带着一个比本实例缓存**更新**的版本到来——因为它上次访问的
  对等实例已经处理过那次发布，或者因为一次总线事件丢失了——本实例会先从 PostgreSQL 重新读取该配置
  项，再决定下发什么。它不会把更旧的版本交给节点，也不会立刻用节点已经持有的版本来应答。
- **响应大小有上限。** 单次响应的内容总量有上限（默认 32 MiB）。超出上限的订阅只返回一个子集，
  其余的在下一次轮询中送达；`BatchGetConfig` 则直接失败，不会截断。

### 一次变更多快到达

发布会先写入版本，再在事件总线上广播；每个实例据此让该键的版本缓存失效，并唤醒注册在它上面的
订阅者。此外还有一轮周期性重同步（默认每 30 秒），从 PostgreSQL 重新读取被订阅配置项的版本，
所以一次丢失的总线事件只会带来延迟，不会带来错误。

项目压测工具的实测结果（`test/load/config_awareness.py`，空闲实例上 200 个探测订阅者、6 次发布，
发布方与订阅方在同一进程内，两侧时间戳来自同一个时钟）：

| 指标 | 结果 |
| --- | --- |
| 被唤醒的订阅者 | 1,200 / 1,200 |
| 端到端 p99（从发起发布 RPC 之前开始计时） | **46.1 ms** |
| 端到端最大值 | 46.8 ms |
| 从 `PublishConfig` 返回时刻起算的 p99 | 38.4 ms |

设计目标是 1 秒。并发能力另有单独测量（`test/load/watch_config.js`）：**单实例上约 10,000 个阻塞中
的 `WatchConfig` 调用**，零失败，0.05 个 CPU 核心，504 MiB RSS。一个阻塞中的订阅者完全不产生 Redis
流量。

**注意。** 一万个节点在同一毫秒内重连，首先是负载均衡器的问题，其次才是服务端的问题。在压测中，
一万条连接的瞬时突发压垮了反向代理的 dial 超时，而此时服务端只占用 0.8 % CPU。请把节点重启错开，
并参见[性能与调优](./17-performance.md)。

### 自己写订阅循环

SDK 已经实现了这个循环，能用就用（见 [SDK 与示例](./14-sdks.md)）。

```python
from spinneret import Client

with Client("https://spinneret.internal", "spn_…") as client:
    with client.config_watcher(["crawler/search.json"]) as watcher:
        item = watcher.get("crawler", "search.json")
        # …… 订阅器在后台线程中长轮询，持续保持 item 为最新
```

```go
w, err := client.NewConfigWatcher(spinneret.WatcherOptions{
    Items:       []spinneret.ConfigKey{{Group: "crawler", Key: "search.json"}},
    SnapshotDir: "/var/lib/mynode/config",
    OnChange:    func(item *spinneret.ConfigItem) { reload(item.GetContent()) },
})
if err != nil {
    return err
}
if err := w.Start(ctx); err != nil {
    return err
}
defer w.Stop()
```

两个订阅器做的是同一件事：先做一次 `BatchGetConfig`，随后循环调用 `WatchConfig`，应用变更并触发
回调。服务端在启动时不可达时，两者都会回退到本地快照，所以节点可以在控制平面故障期间，用它最后
见过的那份配置启动起来。

如果你要自己写这个循环，有五条规则：

1. 从 `version: 0` 开始，之后始终回传你最后收到的版本号。
2. 空响应是超时。重新发起调用；不要当成错误，也不要退避。
3. 出错时退避——SDK 用的是 1 秒起、最多 30 秒——并加上抖动。
4. 防住那种会立刻应答你长轮询的代理：如果一次没有变更的轮询在约 200 ms 内就返回了，先等一会儿再发
   下一次，否则一个配置错误的中间件会把你的订阅变成忙循环。Go SDK 强制了 200 ms 的最小轮询间隔；
   Python 订阅器和自己写的循环需要自己加这道保护。
5. 客户端的截止时间要设得比 `timeout_ms` 大，不能更小。

### 关闭时的行为

服务端排空时，会刻意取消进行中的 `WatchConfig` 长轮询，而让短读取正常完成。节点会看到一次被取消
的调用，退避后重连到另一个实例。这在滚动升级中是预期行为，不是故障。

## 谁能看到哪些配置

配置项没有按站点、按客户端、按节点的定向下发。可见性规则只有两条：

1. **命名空间。** 一个配置项属于一个命名空间。节点的令牌绑定到一个命名空间，读不到范围之外的任何
   东西。
2. **分组。** 令牌的权限范围可以用 glob 限制它能读哪些分组。

| 权限范围 | 授予的权限 | 参数 |
| --- | --- | --- |
| `config:read` | `config:read` | 可选的分组 glob |
| `config:publish` | `config:read`、`config:write`、`config:publish` | 可选的分组 glob |

glob 语言刻意做得很小：`*` 匹配任意长度的字符串（包括 `/`），`?` 匹配一个字符，其余字符都是字面量。
`config:read:crawler*` 能匹配 `crawler`、`crawler.v2` 和 `crawlers`；不带参数的 `config:read`
匹配所有分组，包括 `_runtime`。

控制台用户的权限来自其在命名空间中的角色：

| 权限 | 拥有它的角色 | 允许的操作 |
| --- | --- | --- |
| `config:read` | viewer、operator、admin、owner | 列出配置项，查看内容、版本与差异 |
| `config:write` | operator、admin、owner | 保存草稿，修改 Schema 与描述 |
| `config:publish` | admin、owner | 创建即发布、发布、回滚、删除 |

`config:publish` 也可以作为角色绑定上的**额外权限**单独授予，从而在不把用户提升为 admin 的前提下
给出这一项权力。见[租户、用户与令牌](./11-access-control.md)。

### 定向到部分节点

既然定向是按分组进行的，那就用分组来做。给灰度节点一个不同的令牌和不同的分组或键：

```text
crawler/search.json          由权限范围为 config:read:crawler* 的令牌读取
crawler-canary/search.json   由灰度令牌读取，其权限范围为 config:read:crawler-canary*
```

或者，当节点在其他方面完全一致时，把环境放进键里（`crawler/search.prod.json`、
`crawler/search.canary.json`），让每个节点自身的设置决定订阅哪个键。两种方式都是显式的，都能在控制
台的树里看见，也都不依赖服务端去猜是谁在请求。

## `_runtime` 分组

以 `_` 开头的分组名是保留的。目前只有一个这样的分组：`_runtime`。它是只读的，没有草稿，没有可回滚
的版本，也不能在控制台中创建或编辑。它通过与普通配置项完全相同的读取和订阅协议，暴露实时的调度
状态：

| 配置项 | 格式 | 内容 |
| --- | --- | --- |
| `_runtime/breakers` | `json` | 每个站点的暂停标志，以及它**非关闭状态**的熔断器，按 `<client>/<group>` 索引 |
| `_runtime/site_switches` | `json` | 每个站点的暂停开关，含原因与时间戳 |

```json
{
  "namespace": "prod",
  "version": 7,
  "sites": {
    "example-site": {
      "paused": false,
      "groups": {
        "web/search": {
          "state": "open",
          "open_until": "2026-09-17T10:02:00.000Z",
          "manual": false,
          "reason": "…"
        }
      }
    }
  }
}
```

`_runtime` 配置项的版本在每次熔断状态转移或站点暂停时前进，所以节点可以用 `WatchConfig` 订阅
`_runtime/breakers`，在毫秒级得知某个端点组已被熔断，而不必等到下一次 `Acquire` 被拒绝才发现。

**注意。** 文档**内部**的 `version` 字段是内部计数器，从 0 开始。协议信封中的版本是该计数器加一，
因为在订阅请求里 `0` 已经表示「什么都没有」。请拿协议版本和协议版本比较。

读取 `_runtime` 需要对分组 `_runtime` 具备 `config:read`。带 glob 的令牌权限范围必须匹配它
——`config:read:_*` 或不带参数的 `config:read`——所以权限范围为 `config:read:crawler*` 的令牌看不到
它。

## 控制台页面

**配置中心**，路径 `/config`，位于导航的「配置」分组下。它作用于作用域切换器中选中的命名空间。

![配置中心](../images/config.png)

### 布局

左侧是一棵树，右侧是配置项面板。

树按分组归类并列出其中的键，搜索框同时匹配键与描述。有未发布草稿的配置项会带角标，系统分组标记为
只读。当你有权读取时，`_runtime` 会像普通分组一样出现在树中。

面板有三个标签页：

| 标签页 | 内容 |
| --- | --- |
| **内容** | 编辑器，带实时 JSON 校验、相对 4 MiB 上限的大小指示，以及在文本中找到的密钥引用列表 |
| **Schema 与详情** | JSON Schema、描述、格式、配置项 ID，以及最后的发布人与草稿保存人 |
| **版本** | 版本历史与对比工具 |

### 编辑与发布

编辑器在浏览器内实时校验 JSON——报错精确到行列，解析通过时显示「JSON 格式正确」——YAML 与 Schema
的校验交给服务端，服务端在保存和发布时都会检查。编辑器下方，控制台列出它在文本中找到的每一处
`${secret:…}` 引用，并在你调用服务端之前就标出格式错误的那些（未闭合、路径非法、版本号非法）。
**控制台从不解析引用**，始终显示原文。

「保存草稿」保存草稿。「发布」会打开一个对话框，并排展示已发布版本与草稿的差异、一个备注输入框，
以及即将创建的版本号；未保存的编辑会先被保存为草稿。「回滚」让你挑一个版本，预览
「当前 v12 → v7」；它的备注输入框只是把「回滚到 v7」作为占位提示，并没有预填——不动它就会以空备注
发布这次回滚，所以请自己写一句。

如果在你打开期间有别人改动了这个配置项，面板会提示（「在你编辑期间，该配置项已被他人修改。保存
将覆盖对方的草稿。」），并提供「放弃我的修改并重新加载」。带着未保存的编辑离开页面时会先询问。

### 历史

版本标签页按时间倒序列出每一个已发布版本，含版本号、备注、发布人和时间，标出当前版本，并把回滚
标注为「回滚自 v7」。你可以查看任意版本的内容，对比任意两个版本，或把某个版本与草稿对比，也可以
直接从行内回滚。

### 实时更新

发布会在命名空间频道上发出 `config.published` 事件，所以其他正在查看同一命名空间的控制台无需刷新
就能看到变化。见[可观测性与告警](./12-observability.md)。

## 限额、调优与指标

| 限额 | 取值 | 适用范围 |
| --- | --- | --- |
| 内容大小 | 4 MiB | 每个版本、每份草稿 |
| JSON Schema 大小 | 1 MiB | 每个配置项 |
| 描述 | 1024 个字符 | 每个配置项 |
| 发布备注 | 1024 个字符 | 每次发布或回滚 |
| 单次节点调用的配置项数 | 1–200 | `BatchGetConfig`、`WatchConfig` |
| 互不相同的密钥引用数 | 100 | 每个配置项内容 |
| 响应大小 | 32 MiB | 单次节点读取的内容总量 |
| 分组名 | 1–64 个字符 | 见上文模式 |
| 键 | 1–128 个字符 | 见上文模式 |
| 列表页大小 | 默认 50，最大 500 | 管理类列表调用 |

只有一个服务端变量用于调优配置中心：

| 变量 | 默认值 | 含义 |
| --- | --- | --- |
| `SPINNERET_MAX_WATCHERS` | `20000` | **单个实例**上可同时阻塞的 `WatchConfig` 调用数。超出后新的订阅以 `resource_exhausted` / `rate_limited` 失败，并附带 1 秒的重试提示。 |

其余参数是编译期默认值，不是环境变量：长轮询默认 30 秒、最大 60 秒，被订阅版本每 30 秒重同步一次，
缓存 100,000 个配置项版本，64 MiB 的已发布内容缓存，32 MiB 的响应预算，以及 15 秒的单次数据库操作
超时。

订阅容量是按实例计的，所以整个集群的上限是 `SPINNERET_MAX_WATCHERS` × 副本数。容量估算：一个节点
订阅一组配置项，占用一个阻塞中的调用。一万个这样的订阅大约消耗半个 GB 的 RSS 和二十分之一个核。

| 指标 | 类型 | 含义 |
| --- | --- | --- |
| `spinneret_config_watchers` | gauge | 当前在本实例上阻塞的 `WatchConfig` 调用数 |

请盯住它。指标塌到 0，说明你的节点不再订阅了；指标顶在 `SPINNERET_MAX_WATCHERS` 上，说明节点正在
被拒之门外。

## 安全地变更

### 发布之前

- **加 JSON Schema。** 只要节点会把内容解析成结构体，就给它加一份。这是唯一跑在服务端这一侧的校验。
- **看一眼差异。** 发布对话框展示它是有原因的。发布是即时的、面向整个集群的。
- **写清楚备注。** 这是版本历史将来唯一能拿到的自由文本说明。
- **脚本化发布时使用 `expected_version`**，这样并发的控制台发布会被拒绝，而不是被悄悄覆盖。
- **永远不要粘贴密钥明文。** 用 `${secret:…}`。粘进内容里的值，对该配置项的每一个读取方都可见，
  会永远留在每一个版本里，并会落到节点磁盘上的快照中。

### 灰度发布

服务端会立即把已发布版本下发给所有有权读取它的人。分批是你自己构造出来的，有三种诚实的做法：

1. **每个阶段用不同的键或分组**（见上文）。灰度节点订阅 `crawler-canary/search.json`；你先在那里
   发布，在[可观测性与告警](./12-observability.md)里观察效果，然后把同样的内容发布到
   `crawler/search.json`。显式、可见，而且是唯一一种能证明坏值到不了生产节点的做法。
2. **把开关放进内容里。** 在同一个配置项里带上两套变体，由节点自行判断使用哪一套（`"variant": "b"`，
   或者一个节点用自己名字的哈希去比较的百分比）。要管的配置项少了，但每个节点都会解析这份新内容，
   所以一份能把解析器搞崩的文档会把所有节点一起搞崩。
3. **挑低峰窗口发布**，然后盯成功率。对低风险配置项可以接受，对控制请求构造的那一个绝对不行。

不管用哪一种，都要在发布**之前**就知道回滚路径；并且要知道回滚本身也是一次发布：它同样只用几十毫秒
就能传遍集群。

### 当一份坏配置被发布出去

1. **先回滚，再分析。** 打开配置项，进入版本标签页，选中最后一个已知良好的版本，点「回滚」。它会把
   那份内容重新发布为一个新版本，每个订阅中的节点在一秒内拿到。不要在压力下改草稿再发布——回滚只需
   一次点击，而且不可能引入新的笔误。
2. **确认回滚通过了校验。** 如果在那个良好版本发布之后 Schema 被收紧过，回滚会被拒绝。先移除或放宽
   Schema，回滚，然后在另一次变更中把 Schema 恢复回去。
3. **确认节点确实切过去了。** `spinneret_config_watchers` 应该保持平稳；节点日志中应该出现新版本。
   一个不订阅的节点——只在启动时调用过一次 `GetConfig` 的那种——不会拿到新内容。这正是订阅优于一次性
   读取的理由。
4. **排查还停在坏版本上的节点。** 故障期间断开的节点会从它持有的版本继续；由于比较的是「不同」，
   它们在第一次成功轮询时就会收到回滚后的内容。
5. **事后**补上那条本可以拒绝这份坏内容的 Schema 规则，并对照审计记录（`config.publish`、操作者、
   时间戳）归档这次事件。

### 容易踩的坑

| 情况 | 会发生什么 | 该怎么做 |
| --- | --- | --- |
| 节点仍在读取时删除了配置项 | 节点收到 `not_found`；订阅者不会被唤醒，会继续用手上的旧内容 | 用发布安全值代替删除；等读取方都下线后再删 |
| 发布后密钥被删除 | 节点读取以 `failed_precondition` 失败 | 把被引用的密钥当作关键依赖；轮换用「新增版本」而不是「删除」 |
| 令牌缺少密钥的 glob | 整次配置读取以 `permission_denied` / `scope_missing` 失败，并记为 `config.read` / `denied` | 授予覆盖该配置项所引用全部路径的 `secret:read:<namespace>/<path glob>` |
| 节点持有的版本比某个实例更新 | 该实例会先从 PostgreSQL 重新读取再应答 | 不用管——这是已处理的情况，代价是一次查询 |
| 订阅指标顶到上限 | 新订阅收到 `resource_exhausted` / `rate_limited` | 调高 `SPINNERET_MAX_WATCHERS` 或增加副本 |
| 只在启动时做一次 `GetConfig` | 节点永远看不到变更 | 改用订阅器 |

## 错误

| Reason | 错误码 | 何时出现 |
| --- | --- | --- |
| `not_found` | not found | 配置项不存在、从未发布，或对调用方不可见 |
| `invalid_argument` | invalid argument | 分组或键格式非法、格式值非法、内容语法或 Schema 校验失败、密钥引用格式错误、page token 非法、配置项超过 200 个、互不相同的引用超过 100 个 |
| `permission_denied` | permission denied | 控制台用户在该分组上缺少 `config:read` / `config:write` / `config:publish` |
| `scope_missing` | permission denied | 令牌的权限范围覆盖不到该分组，或覆盖不到被引用的密钥路径 |
| `failed_precondition` | failed precondition | 没有可发布的草稿、回滚到当前版本、被引用的密钥或固定版本不存在、密钥解析不可用 |
| `conflict` | aborted | `expected_version` 与当前版本不一致 |
| `rate_limited` | resource exhausted | 本实例达到 `SPINNERET_MAX_WATCHERS`；约 1 秒后重试 |

全部服务的完整 reason 表见[故障排查](./18-troubleshooting.md)。
